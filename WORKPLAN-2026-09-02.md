## A1 — the code-to-artist index (Perry's stated top priority)

**The bug.** `setCode` writes `codeHash` into the *calling* artist's own show record,
but `requireArtist()` in `_lib.mjs` only ever reads `getShow(DEFAULT_ARTIST)`. So every
artist except Perry gets a success toast for a passcode that can never let them in.
Email is their only door, and when a token expires mid-gig they are locked out on
stage. This is INVARIANT 15d, reintroduced for everyone but the founder.

**Do NOT build a global `sha(code) → artistId` index.** It looks like the obvious fix
and it is the wrong one: two artists who pick the same code collide, and refusing the
second one ("that code is taken") is an *oracle that confirms a working passcode
exists* — a gift to anyone guessing. A global secret-keyed index also makes every
Studio login read one hot global blob, which is the scaling mistake the audit already
found three other instances of.

**Build this instead — scope the code by the artist's page name.** A passcode is half
a credential; the page name is the other half, exactly like a username. The slug is
public, so knowing it grants nothing on its own, and the pair cannot collide.

1. `requireArtist(req)`: when authenticating by bare code, read the artist from
   `?a=<slug>` / `x-admin-artist`, resolve it with `artistBySlug`, and check **that
   artist's** `show.codeHash`. With no slug given, keep today's behaviour and fall
   back to `DEFAULT_ARTIST`, so Perry's existing links and the `ADMIN_CODE` recovery
   key are untouched. Still fails closed (INVARIANT 15c).
2. This means the artist id now comes partly from the request, which brushes against
   INVARIANT 0b. Write the reasoning into the invariant rather than leaving a reader
   to wonder: the *secret* still decides, the slug only says which lock to try. Note
   it explicitly at the call site too.
3. `setCode`: raise the minimum from 4 characters to **8**, and refuse codes on a
   small deny-list (`123456`, the artist's own slug, `password`). Four characters with
   no lockout is a 10,000-guess space.
4. **Add a lockout**, which does not exist anywhere today. A per-artist counter in its
   own blob (`lock_<aid>`): 10 failures in 15 minutes → refuse for 15 minutes, and
   return the *same* generic failure whether the artist exists, the code is wrong, or
   the lock is on (INVARIANT 9h's rule, applied to the code door).
5. `studio.html`: the passcode sign-in needs a "your page name" field beside the code,
   remembered in `localStorage` (`myset.aslug`) and sent as `a=` with every code-authed
   request. Leave it blank and you get the founding artist, as now.
6. Tests: a non-founder signs in with their own code; the *other* artist's code is
   refused for them; a wrong code eleven times locks out; the lockout response is
   byte-identical to a wrong-code response; `ADMIN_CODE` still reaches Perry; a blank
   slug still reaches Perry.

## A2 — money, in severity order

* **A payment is claimed before it is granted** (`_pay.mjs:37,64`, `confirm.mjs:24`).
  A shard write that fails after the claim disables *all three* delivery paths and the
  money is kept. Fix: two-phase claim — write `m.paid[sid] = {…, pending:true}`, grant,
  then flip `pending:false`; treat a pending marker as **not** yet granted so the
  webhook and the reconcile sweep still deliver. This is the last live piece of the
  2026-08-30 "a paid customer got nothing" failure (INVARIANT 5c).
* **A declined request refunds nothing once a song has started**, and tells both the
  artist and the fan that it refunded (`_requests.mjs:139,173`, `admin.mjs:562`).
  Fix: refund to the *stock*, not the flow — record the paid portion on the request row
  when it is created and credit `fan.extra` back for exactly that, and set
  `row.refunded` to what was actually returned so the note stops lying (INVARIANT 0ac).
* **Tapping a free-votes or replay-cost chip mid-round charges paid packs for a round
  that never finished** (`admin.mjs:1073,1189,1260`). Fix: on `freeCredits` /
  `replayCost`, clear `fan.v` but skip the `extra` debit — `prevShow` is already read,
  so the old prices are in hand.
* **A buyer cannot see their bought stock anywhere while the show runs**
  (`show.mjs:110`, `vote.html:328`). `paidLeft` is already sent and never rendered.
  Show free as `remaining/total` plus a `+N bought` chip, and keep that chip visible
  when unlimited is on.
* **`meta.paid` and `meta.tips` grow forever** and are re-read on every Studio poll.
  Cap tips the way gifts are already capped, and move the replay-guard set to its own
  bounded key.

## A3 — the gig, and things that break a night

* **No fetch anywhere has a timeout** (`studio.html`, `vote.html` — zero
  `AbortController` in either). A black-holed request on bar wifi leaves the Studio
  behind a full-screen overlay nothing dismisses. Fix: an `AbortSignal.timeout(~12s)`
  in the shared `api()`/`act()`, a dismissible overlay, and an honest "still trying"
  state. Highest gig-impact item after A1.
* **`clearAllFanVotes` has no read-back verify and swallows a failed shard**
  (`_lib.mjs`), so stale votes can survive a song start — a direct breach of
  INVARIANT 4. Fix: give each shard's `casDoc` a verify, collect per-shard outcomes,
  and return a note from `admin` instead of `.catch(() => {})`.
* **The room can never see a paid play-it-again in Up next**, even when it is exactly
  what "Start top voted" will play. Reproduced: 6 votes on a played song, and the
  audience read "Up next — Nothing yet" while the Studio ranked it first. Fix: feed
  `rankSongs` in `show.mjs` the same union `playTop` uses, flagged `replay:true`.
* **Two gigs in one night: "Start the show" believes the earlier one**, so the late
  set's setlist never switches on (`_events.mjs`, `admin.mjs`). Fix: choose the
  occurrence containing *now* with the latest `startsAt <= now`.
* **After midnight, the set still playing is filed under yesterday's weekday**, above
  "Tonight" (`events.mjs` `dayLabel`). One `if`.
* **A mistyped end time becomes a 12-hour gig** and the feed says "On now" for all
  twelve hours. Fix `durationFrom` to add 1440 only when `b < a`, and cap the
  calendar-derived live window.
* **An impossible clock time is accepted** into a public feed and lands on the wrong
  night. Tighten `normEvent` to `/^([01]\d|2[0-3]):[0-5]\d$/` and reject rather than
  silently defaulting to 20:00.
* **Editing a residency's day leaves a phantom "cancelled" night** on the calendar
  forever (`admin.mjs`) — keep only skip dates the rule would still produce.
* **`eventList` will try to build a ~22MB response** for any window asked of it. Clamp.

## A4 — abuse and honesty

* **Free credits are minted per client-chosen fan id**, so the paid pack is
  reproducible for free in a private tab in about five seconds, and there is still **no
  rate limit on `/api/vote`** anywhere in the tree. Fix: pool the free allocation per
  `(artistId, roomHash)` — already computed at `vote.mjs:38` — so extra ids on one
  network start at zero free, and add a per-room vote ceiling. Note the honest limit:
  this raises the cost of stuffing, it does not end it, and it must never lock out a
  real room sharing one venue wifi (INVARIANT 0ae).
* **The page sells a pack at a scarcity that expires in three minutes** and never says
  free votes come back. Add one line under the pill and in the empty state, and stop
  auto-opening the buy sheet on no-credits. (Note: the auditor judged the underlying
  premise *false* — free credits refreshing is INVARIANT 14 on purpose — so this is a
  copy fix, not a mechanism change.)

## A5 — scale and cost (measured, not guessed)

* **The city picker does 1,241 sequential blob reads at 1,500 artists** (~33s against a
  10s function timeout) and falls back to "No gigs listed yet". Fix: `reindexCities`
  already runs on every gig write, so have it store `{ids, gigs, nextAt}` per city and
  answer `?places=1` from that one document with zero per-artist reads.
* **The city feed re-reads the 245KB registry once per row** — 601 reads and 73MB of
  egress for one 300-artist city. Read the registry once before the loop, `Promise.all`
  in batches, cap the rows.
* **Every audience poll costs 14–15 strong blob reads**, twelve of them all fan shards,
  read even before a show is live and whatever the room size. Store the artist name on
  the show doc so the name backfill never runs; resolve slug→id from a per-slug key;
  skip `readFans` entirely when the show is not live.
* `getShow` is not idempotent with no show doc — `showId`/`updatedAt` change on every
  read, which pins every phone to the 3-second poll rung.
* `carryFans` leaves a paid record and `roomCounts` counts `extra > 0` as present, so a
  brand-new show reports a crowd that is not there.

# B · The new voting flow (Perry's design request)

Tapping **Vote** currently casts one vote instantly. Replace that with a small sheet
that does two jobs at once.

1. **Choose how many votes to cast.** A stepper from 1 up to what this fan can afford
   (`min(remaining, …)`, and unbounded when unlimited), with the cost shown live and a
   replay song priced at `replayCost` per vote. This needs a server change: `/api/vote`
   takes one song and toggles; it will need an explicit **quantity**, with the cap
   enforced server-side (INVARIANT 13 — never trust a client claim) and the whole thing
   still idempotent per `(fan, song)` so a lost response cannot double-charge.
2. **State the rules in plain words, before they commit.** Draft copy, to be checked
   against what the code actually does before it ships:
   * how many votes they have, and **that free votes come back when the next song
     starts** (this is the fix for the false-scarcity finding in A4)
   * that votes they *bought* are a stock that does not refresh
   * what happens when they change their mind. **Decide this first:** today voting is
     idempotent and un-voting refunds (INVARIANT 15). Perry's copy says "once cast it
     is final". Those contradict. Either keep the toggle and say "you can move a vote
     until the song starts", or make multi-vote casts final and change INVARIANT 15
     deliberately — do not ship copy that describes behaviour the code does not have,
     which is the exact failure shape the shipping-discipline skill exists to catch.
   * only mention refreshing the page **if** we keep polling as-is; with the current
     ladder a fan can wait up to 25 seconds, which is the honest reason a manual
     refresh helps. Do not promise live updates the poll cannot deliver.
3. A "don't show me this again" tick, remembered per device, so a regular is not
   nagged every song — but the vote count stepper still appears.
4. Tests: quantity capped server-side, a quantity larger than the balance refused, an
   unlimited fan unbounded, replay pricing per vote, double-submit idempotent.

# C · Venue premium tier

New paid tier for venues. Today `_plan.mjs` covers artists only, so this needs a
parallel plan table for venues plus a `venuePlanOf()`. Free venues keep everything the
room experiences (INVARIANT 0w).

| Feature | Notes |
|---|---|
| **Google + Trustpilot reviews** | Fetch server-side and cache in Blobs, like lyrics. Both have terms about display and attribution — check them, show the source and a real link, never restyle a review into a testimonial. Never invent one (INVARIANT 0j's spirit). |
| **More photos** | Free keeps today's cap; paid raises it. Same magic-byte and dimension checks, same owner key (INVARIANT 0aa). |
| **The verification tag** | ⚠️ **Do not sell the badge.** The audit found `checkDomain` already hands out ✓ Verified on an email-domain match alone, which INVARIANT 0ak says is not proof. Selling it would make MySet's one trust signal purchasable, and a fake ✓ on a real bar sends a real person to the wrong place. Fix the verification first (site fetch + vouches), then let paying venues *skip the queue*, never the proof. |
| **Receiving tips** | Needs the same three delivery paths as artist money (INVARIANT 5c) and its own attribution by `metadata.venue`. Blocked on Stripe Connect, exactly as the artist 10% cut is (INVARIANT 0r) — a venue's tips would otherwise land in Perry's Stripe balance. Say so in the copy rather than shipping a button that misdirects money. |
| **Votes on the venue's own speaker music** | The interesting one. Reuse the artist show engine wholesale: a venue is already a separate account with its own events, so give it a show record and let `/api/vote` serve it. |

For speaker voting, the honest sequencing:

* **Phase 1 — tell a human.** The winning song goes to venue staff as a Web Push
  notification. `_push.mjs` already exists and is spec-verified; this is mostly
  plumbing plus a staff device list. Ship this first: it works with any sound system,
  including a phone on a shelf.
* **Phase 2 — Spotify.** Genuinely possible: the Web Playback SDK and
  `PUT /v1/me/player/queue` can queue a track on an *active* device. The constraints to
  design around, not discover later: it needs **Spotify Premium**, an OAuth
  authorization-code flow with refresh tokens (a real secret to store per venue), an
  already-active playback device, and Spotify's terms forbid using it to build a
  competing jukebox service — read them before building, and check whether a commercial
  arrangement is required. A queue-only integration that never auto-skips the current
  track is both friendlier and further from the line.
* Apple Music has no comparable public queue API. Do not promise it.
