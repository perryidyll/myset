# MySet — Deep audit, 2026-09-02

A full-depth audit: the code, every feature, the pixels, and the cascades a live show sets off.
Fifteen auditors were commissioned across three waves, each with an isolated full-stack sandbox — the real
Netlify functions against an in-memory blob store, seeded with a live show, a second artist and a venue — plus a
headless-Chrome instrument for driving the real pages. Every auditor was required to reproduce what it reported.

## What this run actually covers, and what it does not

**Three of the fifteen auditors finished.** The account's five-hour usage window was exhausted twice by earlier,
wider versions of this run, and a third time part-way through this one. The audit was then parked deliberately:
the running agents were stopped, their sandboxes shut down, and every completed result salvaged from the run
journal so nothing has to be re-earned. **The remaining twelve auditors replay from cache on resume** — their
charges are already written and their prompts unchanged.

What finished, and it is the three hardest slices:

* **the credits and money ledger** — one fan traced end to end, four times, in-process
* **the storage core and the ordering rule** — including a real 40-way concurrency proof
* **the calendar and the city feed** — DST, +05:45 zones, past-midnight sets, and measured fan-out

Not yet run: the vote page and both Studios as pages, the public pages, auth and the security sweep, the pixel
audits, the PWA layer, the repo/doc-drift pass, and the measured cost model. Those are the resume list.

## Each finding

### 1. [critical] "Unlimited votes" silently destroys every pack the room has bought
`S4-01` · area money · kind defect · evidence **reproduced** · invariant 13b  
* files: netlify/functions/_lib.mjs:469, netlify/functions/_lib.mjs:486, netlify/functions/vote.mjs:49, netlify/functions/admin.mjs:1082, netlify/functions/admin.mjs:1073
* what happens: vote.mjs:49 skips the credit check when isUnlimited(fan,show), but paidUsed (_lib.mjs:469) is always creditsUsed-freeCredits with no notion of unlimited, so clearAllFanVotes (_lib.mjs:486) debits `extra` for votes the server gave away free. Every unlimited round eats the buyer's stock until it is 0. paidLeft and carryFans then report the smaller number, so nothing shows the loss.
* how we know: Reproduced in-process against the real handlers (trace1.mjs §D, trace4.mjs §L, `node --import test/register.mjs`). §D: F4 extra=12, freeCredits=3, unlimited on, 7 votes, one play -> `{extra:0}`; the whole 12-credit pack gone in ONE round. §L: extra=15, 8 votes, End show -> /api/show `paidLeft:10`, gift sheet offers 10, newShow leaves extra=10; 5 bought votes vanished. trace2.mjs §J: unlimited on, 6 votes, artist re-taps the SAME free number so resetVotes never fires (admin.mjs:1077) and the next play burns 3: extra 9 -> 6.
* at a gig: Perry taps "Unlimited" for a busy hour so nobody is locked out. The two people who paid $10 for 15 votes are quietly zeroed; when it comes off unlimited they have nothing, and End show says "0 votes left". They paid and the ledger shows no trace.
* smallest fix: Pass the fan id into paidUsed (the bag key is already in scope in clearAllFanVotes/carryFans) and return 0 when isUnlimited(fanId, show). Also add 'unlimited' to RESETTERS (admin.mjs:955) and set resetVotes whenever show.unlimited actually flips, so the pre-toggle round settles at its own prices.

### 2. [high] slug() returns '' for a non-latin title, so a Thai-titled song gets id "" and cannot be voted for
`B1-01` · area storage-core · kind defect · evidence **reproduced** · invariant a song in the payload must be votable  
* files: netlify/functions/_lib.mjs, netlify/functions/admin.mjs, public/vote.html
* what happens: slug() (_lib.mjs:139) strips everything outside [a-z0-9], so a Thai title (any non-latin script, or pure punctuation) becomes ''. addSong mints the id from it (admin.mjs:1115) and returns 200. The song ships in the /api/show payload and renders a normal Vote button, but /api/vote rejects song:"" with 400. The collision guard at admin.mjs:1116 only fires for the SECOND such song, so the first is permanently unvotable.
* how we know: reproduced. t3.mjs (real handlers): addSong {title:'ลาก่อน'} -> 200; getShow library = [{"id":"","title":"ลาก่อน"},...]; /api/show songs[] contains {"id":"","title":"ลาก่อน"}; POST /api/vote {fan:'t1',song:''} -> 400 "missing fan or song". Repeated end-to-end on sandbox 9404: same addSong via curl -> ok:true, then an eval on the real /perryidyll/vote page POSTing {song:""} -> "400 Bad Request", and shot.mjs logged failedRequests: ["http://localhost:9404/api/vote?a=perryidyll HTTP 400"]. Button rendered as onclick="vote('')" at public/vote.html:416.
* at a gig: Koh Phangan, second set. Perry adds a Thai singalong for the staff. It shows on every phone; people tap Vote, the row never changes, and the app looks broken to the whole bar.
* smallest fix: admin.mjs:1115 `let id = slug(title) || 's' + sha(title+'|'+artist).slice(0,8)`, and the same at 525, 588, 1145, 1213; repair a stored id of '' in normShow so existing broken rows become votable.

### 3. [high] importSongs de-dupes on slug(title)|slug(artist), so a CSV of Thai songs imports one row
`B1-02` · area storage-core · kind cascade · evidence **reproduced** · invariant an import never drops a distinct song  
* files: netlify/functions/admin.mjs, netlify/functions/_lib.mjs
* what happens: The bulk-import duplicate signature is `${slug(r.title)}|${slug(r.artist)}` (admin.mjs:1137-1145). Since slug() collapses every non-latin title to '', all such songs by one artist share the signature '|<artist>' and every row after the first is skipped as "you already had". Silent data loss on the one path an artist uses to load a real set list — and the row that survives is the unvotable id-"" song from B1-01.
* how we know: reproduced. t5.mjs: POST /api/admin importSongs with four rows ('ลาก่อน','สวัสดี','ขอบคุณ' all by 'Thai band', plus 'Wagon Wheel'/'Darius Rucker') -> 200, note "Added 2 songs · skipped 2 you already had"; getShow afterwards = [{"id":"","title":"ลาก่อน"},{"id":"wagon-wheel","title":"Wagon Wheel"}]. Two distinct songs gone, reported to the artist as duplicates.
* at a gig: An artist pastes a 30-song list with Thai titles into the importer. It says most rows were songs he already had, one appears in the library, and he has no way to see which were dropped.
* smallest fix: Fall back to the raw normalised title when slug() is empty: `${slug(r.title) || r.title.trim().toLowerCase()}|${slug(r.artist)}`, together with the id fix in B1-01.

### 4. [high] clearAllFanVotes has no read-back verify and swallows a failed shard, so stale votes survive a song start
`B1-03` · area storage-core · kind defect · evidence **reproduced** · invariant every fan write is read back (INV 4)  
* files: netlify/functions/_lib.mjs, netlify/functions/admin.mjs, INVARIANTS.md
* what happens: clearAllFanVotes (_lib.mjs:476-497) passes verify=null to casDoc and wraps each shard in .catch(()=>{}). If one of the 12 fan docs cannot be written, casDoc burns 40 retries, throws 'busy', the error is discarded and the handler still answers ok. Those fans keep last round's picks, counted in the new tally, with credits still used, and the paid settlement in the same loop never runs. carryFans and dropSongVotes share the shape.
* how we know: reproduced by fault injection. t4.mjs wraps the store so writes to f0_perry-idyll return {modified:false}. Two fans on different shards each hold a vote; tally before = {"alpha":1,"bravo":1}. POST /api/admin {action:'play',song:'charlie'} -> HTTP 200 ok:true after 7451 ms. Tally AFTER the start = {"alpha":1}; GET /api/show for that fan reports credits.used 1 with Alpha still flagged mine. INVARIANTS.md:20-24 (INV 4) requires a read-back on every fan-record write; only mutateShow (_lib.mjs:419-433) got one.
* at a gig: Forty phones, blobs stutters on one shard. Perry's next-song tap hangs 7.5s then says it worked; three or four people find their vote stuck on the finished song and their credit gone, and packs bought on that shard are never debited.
* smallest fix: Give each shard's casDoc a verify (every record v.length===0 && spent===0 and extra settled), collect per-shard outcomes, and return a note/err from admin when a shard did not settle instead of .catch(()=>{}). Same for carryFans and dropSongVotes.

### 5. [high] Homepage city picker: 1,241 sequential blob reads at 1,500 artists, 33s, falls back to "No gigs listed yet"
`B6-01` · area scale-cost · kind scale-cost · evidence **reproduced** · prior C018 · invariant 0i  
* files: netlify/functions/events.mjs, public/index.html, netlify/functions/_lib.mjs
* what happens: `?places=1` loops countries -> cities -> countUpcoming, which does `await readEvents(aid)` one artist at a time (events.mjs:19-36,135-145). Reads = cities x min(40,artists) + 1, all serial, uncached: json() sends cache-control:no-store (_lib.mjs:722-727) and index.html:283 fetches cache:'no-store', so every visitor pays it. That fetch is in try{}catch{}, so on timeout index.html:287 renders the blank "No gigs listed yet".
* how we know: reproduced. `node --import ./reg.mjs C-scale.mjs` in /Users/perryidyll/Docs/MySet/_tmp_audit/agents/B6-gigs-time (real handlers, @netlify/blobs swapped for a read-counting fake). World: 1,500 artists, 30 cities of 40 + Koh Phangan with 300. `?places=1 reads=1241 uniqueKeys=1241`; 234ms at zero latency, 5,066ms at 3ms/read, 33,411ms at 25ms/read (Netlify sync budget is 10s). Response body: 1,727 bytes.
* at a gig: Invisible on night one. At a thousand artists a punter opens myset.vip, waits, and is told "No gigs listed yet" for a city with 300 gigs on - and the bill is 1,241 blob reads per page load.
* smallest fix: Keep the counts in the cityindex document: reindexCities already runs on every gig write, so have it store {ids, gigs, nextAt} per city and answer ?places=1 from that one doc with zero per-artist reads. Failing that, Promise.all with a concurrency cap plus s-maxage on the picker response.

### 6. [high] City feed: uncapped serial fan-out re-reads the 245KB registry per row - 601 reads, 73MB egress for one page
`B6-02` · area scale-cost · kind scale-cost · evidence **reproduced** · prior C049  
* files: netlify/functions/events.mjs, netlify/functions/_auth.mjs
* what happens: events.mjs:68-86 walks `for (const id of ids)` with awaits inside and no cap, and each iteration calls artistById(id) = readArtists(), a read of the single global registry doc (_auth.mjs:72-75). N artists in a city costs 2N serial reads, N of them the same big blob, uncached. Rows are unbounded too: 300 residencies produced 300 rows in one response, growing linearly with the city.
* how we know: reproduced. Same run as B6-01: `city feed KP reads=601 uniqueKeys=302` - 299 redundant reads of `artists`. Registry doc measured 245,777 bytes, so 300 rows re-read = 73.7MB per request (script prints `registry bytes re-read per city-feed request = 73733100`). 347ms at zero latency, 9,159ms at 25ms/read.
* at a gig: A tourist on bar wifi taps Koh Phangan to see who is playing tonight, gets a spinner then nothing, on the one night the town is full - and that request pulled 73MB out of the blob store.
* smallest fix: Read the registry once before the loop and look ids up in reg.byId instead of calling artistById per row; Promise.all the readEvents calls in batches of ~10; cap ids and emitted rows; add s-maxage so a busy city is computed once a minute, not once a phone.

### 10. [high] Tapping a free-votes or replay-cost chip mid-round charges paid packs for a round that never finished
`S4-04` · area money · kind defect · evidence **reproduced** · invariant 13b

### 11. [high] Free credits are minted by rotating the fan id — the paid pack is reproducible for free in a private tab

### 13. [medium] getShow is not idempotent with no show doc: showId/updatedAt change every read, pinning phones to 3s polls
`B1-04` · area storage-core · kind defect · evidence **reproduced** · invariant two reads of an unchanged show agree  
* files: netlify/functions/_lib.mjs, public/vote.html
* what happens: normShow spreads defaultShow() (updatedAt = Date.now()) over the stored doc, then derives showId = 'show-'+updatedAt and startedAt from it (_lib.mjs:366-402). For an artist with no show document yet, every read invents new values. vote.html:659 puts updatedAt in the poll signature, so the ladder never quiets and every phone stays on the 3s rung at ~15 strong reads a poll.
* how we know: reproduced. Two consecutive L.getShow() on a minimal stored doc gave showId show-1788334984545 then show-1788334984546 (startedAt likewise). * at a gig: A new artist shares his vote link the day he signs up, before touching the Studio. Every phone that opens it polls every 3s forever instead of easing to 10-25s — the account earning nothing is the most expensive one on the platform.
* smallest fix: Derive only from stored fields: `const at = s && s.updatedAt; show.showId ||= at ? 'show-'+at : 'show-pre'; show.startedAt ||= at || null;` and leave updatedAt null until a write. Or write the default show doc at createArtist.

### 14. [medium] The audience's Up next can never show a paid play-it-again, even when it is what playTop will start
`B1-05` · area vote-page · kind defect · evidence **reproduced** · prior C038 · invariant one ordering rule, one visible ladder (12b)  
* files: netlify/functions/show.mjs, public/vote.html, netlify/functions/admin.mjs
* what happens: show.mjs:52-56 ranks only `pool.filter(s => s.id !== nowPlaying && !played.includes(s.id))`; played songs ship in a separate `played` array. vote.html:313-314 builds Up next from `d.songs.filter(s=>s.votes>0).slice(0,3)`, so a played song holding replay votes is structurally excluded from the room's ladder — while playTop (admin.mjs:1029-1033) and stage.mjs include it. One rankSongs, two different input sets.
* how we know: reproduced. t3.mjs: Wagon Wheel played, then six fans voted for it. ## Fixed and shipped in this pass

Four fixes, each with a test that fails without it. The suite is now **262 assertions**, up from 237.

### 1. "∞ Unlimited" was comprehensively broken — two independent bugs in one feature

The switch meant for a paid private party did two things at once, and neither was voting.

* **It destroyed every pack the room had bought.** `vote.mjs` skips the credit check entirely while unlimited is
  on, so nothing is ever owed — but `paidUsed()` had no notion of unlimited and read the vote count as paid, so
  `clearAllFanVotes` debited `extra` at the end of the round for votes the server had given away free. Measured by
  the ledger auditor: **a 12-credit pack gone in one round.** `paidUsed` and `unspentPaid` now take the fan id
  (both callers already had it — it is the shard key) and return 0 when that device votes without limit.
* **It disabled every Vote button in the room.** The server sends `remaining: null` when unlimited, and
  [vote.html](public/vote.html) tested `c.remaining < cost`. In JavaScript `null < 1` is `true`, so every row
  rendered `disabled` while the pill cheerfully showed ∞. Thirteen lines below, the ask-card rule already had the
  `!c.unlimited` guard, which is what makes this an oversight rather than a design.

Verified in a real browser after the fix: 58 vote buttons, **0 disabled**, pill reading ∞, and a tap moved the
server's tally from 10 to 11.

### 2. A song titled in Thai could never be voted for

`slug()` keeps only `[a-z0-9]`, so a title with no Latin letters or digits — Thai, Japanese, Cyrillic, an emoji —
slugged to the **empty string**. The song entered the library with id `""`, which no vote can name: the room could
not see it and the artist could not see why. On Koh Phangan that is not an edge case. Worse, `importSongs`
de-duplicated on `slug(title)|slug(artist)`, so a CSV of Thai songs collapsed to a single row.

There is now one definition of a song id, `songId()`, used by all four mint sites (add, import, accept a request,
starter setlist), falling back to a hash of the title so the id stays stable and derived from the song; and one
`songSig()` for import de-duplication. A Latin title is byte-for-byte unchanged (`Hey Jude` → `hey-jude`).

### 3. A comment that argued for rungs the code does not have

The polling-ladder comment in vote.html reasoned about a 6-second middle rung and called it shipped. The code has
always said 10 seconds. The comment now quotes the real rungs, 3 / 10 / 25.
