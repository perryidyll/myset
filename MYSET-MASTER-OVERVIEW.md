# MySet — Master Overview

**The single document that explains MySet completely: what it is, what every rule is,
how it is built, and why each decision went the way it did.**

Written for a capable model or engineer arriving with no history — Claude, Codex,
Gemini, Grok, or a person. Nothing here assumes you were in the room for any of it.

---

## HOW TO USE THIS DOCUMENT

### MySet in sixty seconds

A live audience, in a bar, votes from their phones on which song the musician plays
next. The musician sees the running tally on stage and plays the winner.

That is the whole product in one sentence, and everything else exists to make that
sentence true in a real room: with bad wifi, with people who will not install an app,
with a performer who has one hand free between songs.

It is **live at https://myset.vip**, taking **real money** through **real Stripe
accounts**, run by one person. `main` **is** production.

### The eight rules of working in this repository

Read these before you touch anything. Most were learned by breaking something.

1. **`main` IS production.** A push to `main` deploys to myset.vip in about a minute.
   No staging, no review gate, no approval step. A bad commit is a live outage during
   somebody's show.
2. **Nothing may break the gig.** Every failure must degrade to *"the room can still
   vote"*. That is the ranking function for every trade-off in this codebase.
3. **The audience never signs in.** Anonymity is why it works in a bar. Any design that
   needs a fan to have an account is the wrong design.
4. **Never show the room a button that leads to a shrug.** If the server will refuse it,
   the page must not offer it — and if the page offers it, the server must allow it.
5. **Never claim what you have not run.** Say "verified" only about things you executed
   and can quote the output of. Everything else is "not checked". An honest gap beats a
   confident guess.
6. **Numbers come from the code, never from memory.** Every figure in §2.1 of this
   document is generated by `tools/overview.mjs`. If you need a number that is not
   there, read the source and add it to the generator.
7. **Another session may be editing this repo.** Check `git status` before you start. If
   there are changes you did not make, stop and say so.
8. **Money, sign-in and storage are not places to be clever.** `netlify/functions/` holds
   payouts, sessions, roles and Stripe. Read `INVARIANTS.md` before changing anything in
   it, and write a decision record (Part 7) when you do.

# PART 1 — THE RULES OF VOTING

*This is the heart of the product. Every other part of MySet exists to serve it.*

## 1.1 How a vote behaves today

> **A vote is spent the moment it is cast. It stays on that song until it is played
> or the night ends — unless the artist declines the song or request, which returns
> its votes.**

**This is the current behaviour, not a hard rule.** The user, 2026-09-12: "that was
never meant to be a hard rule, and currently votes do go back if the artist declines
the vote/request." It may change; the rest of Part 1 describes how it works now.

Perry, 2026-09-07, settling it:

> *"the votes do NOT go back to the audience members whose song(s) were not chosen!
> they stay attached to the song(s) you voted for and that song stays in the queue
> until it is played or the show is over. if they paid for votes and their song doesn't
> get played, they lose the money and the votes… that's the whole game. but they don't
> really lose because they're tipping the artist and that's the whole point."*

Everything below follows from that rule. Decision records:
[`0001-a-vote-never-comes-back.md`](docs/decisions/0001-a-vote-never-comes-back.md) and
its narrow successor,
[`0016-an-artist-declined-unplayed-song-returns-its-votes.md`](docs/decisions/0016-an-artist-declined-unplayed-song-returns-its-votes.md).

**Before 2026-09-07 this was not true**, and any document, comment or model memory
describing a board that resets between songs is describing the old product. The
function that did it (`clearAllFanVotes`) is deleted, not disabled.

## 1.2 The objects

| | What it is | Where it lives |
|---|---|---|
| **A show** | One night. Has a status (`pre` → `live` → `ended`), a setlist, a played list, a now-playing, and every price the artist has set | one document, `show_<artistId>` |
| **A song** | Title, artist, key, genres, and whether it is switched on | inside the show document |
| **A fan** | One phone. A random id in that phone's own storage. **Never a person, never an account** | sharded across `f0…f11_<artistId>` |
| **A vote** | One song id in `v`, plus its `[cost, paidCredits]` source tuple in `va[songId]` | on the fan record |
| **The board** | The tally, computed by counting every fan's `v` | never stored — always derived |

A fan holding three votes on one song has that song id in `v` three times. `voteCounts`
and `creditsUsed` both work by counting entries, so multi-vote came out of the existing
shape rather than a new field.

**Ties are broken by whoever voted first.** Each fan stamps `ts[songId]` on their first
vote for a song and it is never overwritten, so adding a fourth vote does not move a
song up the tie order.

## 1.3 What a vote costs

| | Cost | Set by |
|---|---|---|
| A song not yet played tonight | **1 credit** | fixed |
| A song already played tonight (a "play it again") | **the replay cost**, default 5 | the artist, in Settings |
| A song request (something not on the list) | **3 votes by default**, plus an optional whole-dollar offer at $1 = 1 paid vote | the artist; **off by default** |
| A birthday shout-out | costs **votes**, default 3 | the artist; **off by default** |

Every request has a vote-only path. Birthday shout-outs remain vote-only; an off-setlist
song request may add an optional card authorization that is captured only after the
artist plays and finishes the song.

Every default is generated into §2.1 straight from the source.

## 1.4 The credit ledger

Each fan record carries these ledger fields for the night:

| Field | Meaning | Behaviour |
|---|---|---|
| `used` | every credit spent tonight | rises at spend; decreases only for an explicit artist decline/refund |
| `freeUsed` | how much of `used` came out of the free allowance | stamped at spend; its matching portion is restored on decline |
| `extra` | credits bought with money, a real balance | carries between shows |
| `va` | `[cost, paidCredits]` for each held vote, grouped by song | makes paid counts and exact decline refunds derivable |

**Paid spend is `used − freeUsed`.** Free credits are always spent first.

**Spend cannot be derived from `v`, and this is the subtlety that makes the rule work.**
It used to be: `v` held every vote a fan still had, so counting it gave what they had
spent. A played song now removes its votes from `v` — so a derived count would hand the
credits back at the exact instant the rule forbids it.

**`freeUsed` is stamped at the moment of spending, not worked out at the end**, because
the artist can change the free-credit number mid-show. Computing the free portion
against whatever number happens to be there at the end would re-price votes already
cast, and debit somebody's paid pack for credits they took from the free allowance.
That was a real bug on the old path; stamping makes it unreachable.

A fan record written **before** 2026-09-07 has no `used`, so it is derived from `v`
once, on its next cast, and stored like everyone else's from then on.

## 1.5 Casting a vote — the whole path

`POST /api/vote` with `{fan, song, n, cast}`. In order:

1. **Method, body, ids.** `n` is clamped to 1–50 — the affordability check is what
   actually bounds it; the cap only stops a hand-made request turning one fan record
   into a million-element array.
2. **The cast id.** `cast` is a random id minted when **Confirm** is pressed, not when
   the sheet opens (stepping the quantity would reuse it). A malformed id is **refused**
   rather than ignored: silently dropping it removes the one thing it exists to provide.
3. **Show state.** Ended → 409. Song not on the list → 404. Song is playing right now →
   409.
4. **Inside the fan mutation** (so two racing retries cannot both get past it):
   - voting window closed → 409, and **no changes at all**, in or out
   - **already-seen cast id** → return exactly what it returned the first time and write
     nothing
   - `op:'clear'` from a cached page → *"Those votes are cast — they stay with the
     song"*, 409
   - not affordable → 402 `no-credits`
   - **charge, attribute, then push.** `chargeVotes()` moves `used` and `freeUsed`
     while appending each vote's `[cost, paidCredits]` source tuple; then `n` song ids
     go into `v`; then `ts[song]` is stamped if absent
5. **Read back after writing.** If the votes did not stick, retry. Compare-and-swap
   alone is not enough on this store (INVARIANT 4).

**There is deliberately no head-count check.** A room over its plan's size does not stop
taking votes — see §1.13.

**Charging happens at the cast.** It used to happen at the round reset, deliberately,
because un-voting would otherwise burn a paid vote. With no un-vote and no round, the
cast is the only honest moment left — and it killed a trap on the way: a replay used to
be priced at 1 instead of the replay cost if the ledger settled after `play` moved the
song out of the played list.

**There is no un-vote.** The endpoint has no path that removes a vote at a fan's
request.

## 1.6 What ends a vote's life

| Event | What happens to the votes on that song | Does anybody get credits back? |
|---|---|---|
| **The song is played** | taken off the board (`consumePlayedVotes`) | **No.** `used` does not move |
| **The artist hides or removes the song** | taken off the board | **No** |
| **The artist taps Decline + refund votes on an unplayed song** | song is hidden; votes are removed | **Yes — exact free/paid credits are restored** |
| **The artist clears the board** | every song's votes go, all at once | **No.** The Studio says so before the tap |
| **The show ends** | the board is gone with the night | **No** |
| **A new show starts** | fan records are rebuilt; only **unspent bought credits** survive | Only bought credits, and only if unspent |

## 1.7 The complete "do I get it back?" table

| Situation | Credits back? |
|---|---|
| Your song was not played and the night ended | **No** |
| Your song was played | No — you got what you paid for |
| The artist deleted the song you voted for | **No** |
| The artist cleared the board | **No** |
| You tapped by mistake | **No.** There is no un-vote |
| The artist declined your **song request** | **Yes** |
| The artist explicitly declined an **unplayed setlist song** | **Yes — its attached votes return** |
| You **bought** credits and never spent them, and the show ended | They **carry to the next show**, unless you choose to gift them |
| The artist ended the show by accident and restarted it | Your gift pledge is quietly cancelled and you are made whole |
| An artist deletes a song the room paid to hear | They keep the money. Nothing in the code stops them (INVARIANT 15) |

The request refund exists because **nothing was ever put on the board for it**. The
setlist-song refund is different: `refundSongVotes` removes votes that were on the
board and restores the exact free/paid split recorded when each vote was cast.

## 1.8 Buying votes

- **Vote packs**, priced by the artist. Defaults in §2.1, clamped server-side to $1–$500
  and 1–100 votes.
- Bought votes are a **stock**: they do not refresh, they **carry into the next show**,
  and free credits are always spent first.
- **Never granted from a client claim.** A payment is verified server-side and has
  **three independent delivery paths** (§4.3).
- When a show ends, a fan holding unspent bought credits is asked: carry them, or let
  the artist keep them. **Doing nothing carries them** — never silently pocket what
  somebody paid for. The gift is a *pledge*, honoured only at the real end-of-show
  boundary, so an accidental End that gets restarted cancels it invisibly.

## 1.9 Unlimited

Two switches, both the artist's:

- **The whole room is unlimited** — everybody votes as much as they like.
- **One device is unlimited** — the artist's own phone, so they can test without eating
  the audience's credits.

An unlimited device is **charged nothing but still has its ledger stamped**, so `used`
stays honest if the artist turns unlimited off mid-show. Without that, spend would fall
back to being counted out of `v` and the votes they were given free would start costing
them. (Measured, before this was fixed: a 12-credit pack vanished in one round.)

**`unlimited` has no plan gate at all.** Deciding everyone votes freely is running your
show, not pricing it.

## 1.10 What the fan is told, word for word

This design is only fair if nobody finds out afterwards. So the confirmation sheet says
it in the approved wording and emphasis **before** anybody confirms:

> You have **6** votes right now.
>
> *(and, if they have bought any)* You also have **4** votes you bought — those are
> yours to keep until you spend them.
>
> Once you confirm, it's final! Votes **can't be changed** once cast and ***don't come
> back***.

Under the Confirm button: *"Are you sure? Votes can't be changed!"*

**Two tests read that text out of the shipped file** rather than trusting the code to
behave. The words are the promise.

## 1.11 Concurrency, retries and failure

- **A cast is idempotent by its own id**, not by state. Before finality, voting toggled,
  so a lost response found the vote already there and removed it — self-correcting, and
  never a double charge. That mechanism is gone, so without an id a dropped response on
  bar wifi casts a second time, at replay prices. (INVARIANT 15h.)
- **Fan records are sharded across 12 documents** so a burst of voters does not contend
  on one key. Load-tested: **80 simultaneous voters, zero lost votes.**
- **Every fan write is re-read after writing** and retried. On this store a conditional
  write can report success without sticking.
- **A fan can never spend more than they have**, and it is enforced on the server. The
  page's stepper is a convenience, not a control.
- **The artist id comes from the session or the host, never from the request body.**

## 1.12 Big rooms

Nobody is ever refused. The room **slows down and shortens** instead. The exact rungs
are generated into §2.1.

- **The server sets the pace.** `pollFloorFor(heads)` returns the fastest interval a
  room may use; the payload carries it as `nextPollMs`; the page builds all three rungs
  off it. At the default floor an ordinary gig feels exactly as it always has.
- **The board shortens, and says so.** Anything **this fan voted for** is concatenated
  back on regardless of rank — a song that silently vanishes reads as a lost vote, not
  as a shorter list. The page labels it: *"Big room tonight — showing the top 15. Songs
  you voted for stay on your list wherever they are."*
- **The plan's audience number is a billing line, not a door.** It is stamped onto the
  show when the night starts, so an artist who upgrades mid-set does not have the room
  change size underneath them.

This is the market's own answer, not an invention: Mentimeter publishes it as policy,
and YouTube's only hard caps in Live chat are on spend and on attention, never on how
many people may watch. Decision record
[`0006`](docs/decisions/0006-a-full-room-is-never-refused.md).

### Two things a room is protected from (added 2026-09-11)

**A script casting votes.** Every fan record carries a small token bucket: a device may
cast a burst of votes in a row and then a steady number a minute after that (the exact
figures are in §2.1). It is checked inside the write that already happens, so it costs
no extra read, and a refused cast writes nothing — which is the point, because the hole
it closes is somebody running up the write bill, not a fan voting enthusiastically. A
person tapping as fast as they can stays under it. Decision `0030`.

**A bug nobody can look at afterwards.** Netlify deletes function logs after 24 hours.
So the server now writes its own errors into the blob store, one document per hour
under a computable key, and the voting page has a **"Something wrong?"** link. A report
carries the fan's sentence, the last twenty things the page saw fail, and the last three
hours of the server's own errors — and the artist reads it in the Studio, under the
money. No vendor, no account, no new dependency. Decision `0029`.

**What MySet cannot do, and will not pretend to.** It cannot tell that Safari and Chrome
on the same phone are the same person; the fan id lives in the browser, and browsers do
not share it. Nothing on the web can, honestly. Matching by network address is worse
than nothing: everyone on the bar's Wi-Fi shares one address, and a phone on mobile data
changes its address mid-set — so a network rule either locks out the whole room or does
nothing. What MySet does instead is stamp each fan record with a per-show hash of its
network (INVARIANT 0ae), so the artist can see when one network is producing many
"phones", and it keeps the free allowance small enough that a second browser is worth
a handful of votes, not a swing. The votes that decide a night are the paid ones, and
those cost real money per browser.

## 1.13 Between shows — the dark room

A fan who opens the page with **no show running** sees the **setlist, whole and quiet**:
every song back in the list, no votes on anything, nothing claiming to be playing, and
every song priced at 1 rather than at last night's replay cost.

**Nothing is deleted to do this.** It is display, and only display — the show record is
untouched, so *"Resume it instead"* still finds the night exactly as the artist left it,
and the Studio reads a different endpoint so the artist always sees the truth.

The **Tip** button is always there, across the full width, because there are no votes
left to buy and the minute after a night ends is exactly when somebody decides it was
worth something.

## 1.14 Last call

**Studio → Live tab**, only while a show is running: an orange-ringed **Last call**
button. Tapping it counts down on the button itself, so the artist can see it going and
cannot fire a second one over the first. Every phone in the room gets a full-width box
at the top with a big number ticking to zero.

- **It sends time LEFT, not the moment it ends.** A phone whose clock is four minutes
  fast would read an end time as long past and show nothing at all.
- **A later poll can never shorten a running countdown.** A box that jumps backwards
  reads as broken.
- **It is a nudge, not a lock.** Voting stays open at zero. There is already a switch
  for closing voting, and a button that silently does two things is the harder one to
  explain on stage.
- **Honest limit:** phones only learn about it when they next poll, so somebody may open
  on "7" rather than "10" — and in a big room, where the interval is deliberately
  longer, some phones will not see it at all. That is the cost of not holding a socket
  open per person (Part 7 of `docs/reports/open-line.md`).

## 1.15 What the artist can do to the board

| Action | Effect on votes |
|---|---|
| **Start the top-voted song** | that song's votes come off; every other vote stands |
| **Start any song** | same |
| **Undo a played song** | it goes back in the list; its votes are already gone |
| **Pause voting** | no votes in or out; the tally is untouched |
| **Hide or remove a song** | its votes come off the board; nobody is refunded |
| **Decline + refund an unplayed song** | it is hidden; every attached vote and its exact free/paid credit source return |
| **Clear the board** | every song's votes go at once; **nobody is refunded**, and the confirm says so |
| **Change the free-vote number mid-show** | applies to future casts only — already-stamped `freeUsed` is never re-priced |
| **End the show** | the board goes with the night; unspent **bought** credits survive |

## 1.16 What was deleted on 2026-09-07, and why it matters

If you find a reference to any of these, it is stale:

`clearAllFanVotes` · `releaseUnvotable` · `releaseNote` · the **`voteFinal` feature
flag** · the un-vote branch in `vote.mjs` · `openUnvote` and `VMODE` in the page · the
twelve-shard sweep that ran whenever an artist narrowed the setlist.

That last one is a saving, not a loss: `test/cost.mjs` used to assert that narrowing the
setlist read all twelve fan shards, and now asserts it reads **none**.

**One bug was introduced and caught in the same change:** `roundVotes` in the show log
was the whole board's total, which was correct only while each round's votes were a
separate set. With votes standing it would have counted the same standing vote again at
every play, and a quiet night would have reported thousands in the Money tab. It is now
the votes that song collected. One vote, counted once: when its song plays, or in
`leftover` if it never does.

| `cut` | the platform's share of every tip, vote pack and merch sale | `_connect.mjs`, as a Stripe `application_fee_amount` on a direct charge |
| `gigs` | how many shows may be **started** in a UTC calendar month | `admin.mjs` and `_lifecycle.mjs` — both the button and the scheduler go through one function |
| `featured` | how many songs are **live to the audience** at once (never how many are stored) | `admin.mjs` on `toggleSong`, and the payload builder |
| `audience` | a **soft** ceiling stamped onto the show; the room slows and shortens, nobody is refused | `_lib.mjs` (`pollFloorFor`, `boardLimitFor`), `show.mjs` |
| `seats` | team members who can sign in | `_account.mjs` |
| `pricing` | setting your own vote-pack prices, replay cost and request costs | `admin.mjs`, 402 |
| `setlists` | **creating** a named setlist. Only creating — an artist who made sets on Plus and drops to free keeps using, renaming, filling and deleting them, because **a cap never deletes anything** | `_lists.mjs` |
| `merch` | selling items from the community page | `_plan.mjs` `merchAllowed()`, checked by the Studio, the checkout **and** the page — one answer, three readers |
| `moderate` | **deleting** a fan's post for good. **Hiding is free on every plan, for ever** | `_plan.mjs` `moderateAllowed()` |

**Hiding is free and always will be.** Every artist must be able to take something
offensive off their page the second they see it. What a paid plan buys is *erasing* it.
And because `/api/img` and `/api/vid` serve by URL and know nothing about a post being
hidden, **hiding deletes the bytes** — the words stay and can be un-hidden.

**The founder bypass is load-bearing.** Perry predates the registry, so `planForArtist`
returns "free" for him. `merchAllowed` and `moderateAllowed` both bypass on
`isPlatformOwner`, and both are the single answer used by every caller.

## 2.3 Why the free tier is capped by gigs and not by features

Every phone in the room polls for the whole gig, so what MySet costs to run is driven by
**gigs played**, not by artists signed up. Capping free on the real cost driver is what
makes free survivable. **Four shows a month is a hobbyist; five is somebody earning from
it.**

Counted in **UTC calendar months**, resetting on the 1st, and **stamped onto the show
record** — so what the Studio shows and what the server enforces are computed the same
way, and the count cannot be fudged from a phone.

Decision record
[`0003`](docs/decisions/0003-the-free-tier-is-capped-by-gigs-not-features.md).

## 2.4 "Plus feature" versus "Coming soon"

Locked features are **shown, greyed out — never hidden**. Perry's call, and it fixed a
real shrug: the pricing controls were fully tappable on free and the server refused them
with a 402.

Two states, and the difference is honesty:

- **`.lock`** — built, and a higher plan turns it on. The veil is a button; tapping it
  scrolls to the plan cards. Reads *"Plus feature"* / *"Pro feature"*, naming the
  **cheapest** plan that actually has it.
- **`.lock.soon`** — designed and **not built**. Greyed on **every** plan including Pro,
  not tappable, reads *"Coming soon"*.

`pointer-events: none` is the lock; opacity is only how it looks. A lock that is only
opacity is not a lock, and there is a test for it.

The styling is `public/lock.css`, linked by **both Studios and nothing else** — it was
first written into `app.css`, which looked right and did nothing whatsoever, because
neither Studio loads `app.css`. Caught by measuring computed styles in a browser.

Decision records [`0004`](docs/decisions/0004-locked-features-are-shown-greyed-not-hidden.md)
and [`0005`](docs/decisions/0005-an-unbuilt-feature-is-never-shown-as-yours.md).

## 2.5 The venue ladder

Generated in §2.1. Two rows only — there is no $10 venue tier, so venue merch sits on
Pro.

**Venues get paid the way artists do**: Stripe Connect Express keyed `v_<venueId>`,
direct charges on the venue's own account, with the Getting-paid card and the orders
list on the Venue Studio's Merch tab. The one difference Perry asked for: **Stripe's
card fee is shared evenly** on both venue rows (§4.4).

`reviews` left the not-built list on 2026-09-04 — the community page **is** reviews —
and is free on both rows, because **what the room reads cannot be Pro-only.**

## 2.6 Paying for a plan

**Stripe Billing holds the subscription; the registry holds a mirror.** `_billing.mjs`
keeps one `billing_<owner>` document of pointers (customer, subscription, price key,
period end, whether the retention month was used) and writes the *plan* onto the
registry row, so every existing reader is unchanged.

- **Prices are found by lookup key** and created on first use — never a hard-coded
  `price_…` id.
- **Two ways to learn the truth**: Stripe's webhooks
  (`customer.subscription.updated`/`.deleted`, `invoice.payment_failed`,
  `checkout.session.completed`), and a belt — the return trip from Checkout reads the
  session from Stripe **by id** and checks it belongs to the owner, and `maybeSync`
  re-reads the subscription at most every six hours. **A URL saying `?sub=done` changes
  nothing by itself.**
- **Leaving is gentle.** Paid → free is `cancel_at_period_end`; paid → paid is a price
  swap with proration; the plan keeps **three days' grace** after the period end. The
  **retention offer** — 50% off one more month — is a real coupon on the live
  subscription, recorded as offered and used, and refused server-side the second time.
- **Comps still work exactly as before**: a comp is a registry row with no subscription
  behind it, and a comped period that runs out falls back to free.

## 2.7 The account can leave

`accountExport` returns everything MySet holds about an artist as one JSON file (never a
fan's device id). `accountDelete` (owner only, the word `DELETE` typed, **two screens**)
cancels the subscription, un-indexes the calendar and the schedule, and marks the row —
a **thirty-day soft delete in which not one document moves**: the page 404s, billing
stops the same day, and one tap undoes it. The founder cannot be deleted from the app.
Full design in `ACCOUNTS.md`.

## 2.8 What is free today, on every plan

**Not a rule** — the user, 2026-09-12: "anything the room experiences is free" is too
strong a statement for something relatively unimportant and subject to change. What
follows is the list as it stands. Lyrics were briefly behind a paywall and were put
back: an audience that gets a sing-along at one gig and not the next learns that MySet
is unreliable, which costs more than the subscription is worth.

That covers: voting itself, the lyrics sheet, pull-to-refresh, the community page,
hiding an offensive post, the gig calendar, the city feed, and the whole Studio's
show-running surface.

and sound come out **bit-identical**. Upload is chunked (raw bytes, never base64) so no

# PART 4 — THE MONEY

## 4.1 What the audience pays

Vote packs, tips, direct paid replay votes and optional off-setlist song-request offers
use Stripe. Every request still has a vote-only path, and birthday shout-outs remain
vote-only. A request offer is authorized at submission, captured only after the artist
finishes the song, and released on decline or an uncompleted show end.

## 4.2 How the money moves

**Stripe Connect, direct charges.** The charge is created **on the artist's own Stripe
account**. The money is legally theirs and MySet takes a platform fee off the top. This
encodes an identity: *MySet is not selling the night — the artist is, and MySet provides
the infrastructure.*

**The trade, stated plainly:** with direct charges, Stripe's own processing fee
(~2.9% + 30¢) is charged to **the artist**, not to MySet. On a $5 vote pack a Plus artist
pays roughly 45¢ to Stripe and 50¢ to MySet. ***"10% to MySet" is not "you keep 90%."***
The Studio says this before an artist onboards.

**Onboarding** is Stripe-hosted Express, so MySet never sees a bank detail. The country is
asked for and validated — an Express account's country **cannot be changed afterwards**,
and getting it wrong means an artist can never be paid out properly.

**Nobody takes money until Stripe says so.** The gate is Stripe's own `charges_enabled`,
never a local "they clicked onboarding" flag. **Started is not ready.**

Decision record
[`0007`](docs/decisions/0007-money-is-charged-on-the-artists-own-stripe-account.md).

## 4.3 Three delivery paths, because one was not enough

1. the buyer's browser returning to the voting page (or the community page, for merch)
2. a Stripe webhook, independent of the buyer's phone
3. a reconcile sweep the artist can run from the Studio

A payment is **claimed before it is granted** so a race cannot grant twice — but the claim
is marked **undelivered** until the votes actually land, so a failure leaves the money
*owed* rather than silently settled, and the sweep picks it up. The grant is recorded per
buyer per purchase, so a retry can never hand out the pack twice.

**Money is attributed by tag, never by timestamp.** Perry's Stripe account holds unrelated
charges; an early version reported **$133 of somebody else's business** as MySet revenue.

## 4.4 The venue fee split

On any plan row with `splitFee` (both venue rows), the application fee is

```
max(0, floor(amount × cut) − round((amount × 0.029 + 30) / 2))
```

A $50 item on venue Free sends MySet 412¢ instead of 500¢; on venue Pro 12¢ instead of
100¢; **a $12 item on Pro sends nothing at all**, because the fee floors at zero. It is an
estimate at checkout and the Studio says so. The exact figure comes later from the balance
transaction, settled with a fee refund (`_feesplit.mjs`), and only bites above about $29 —
below that MySet's fee is already zero and there is nothing to split. **Artists are not
split.**

## 4.5 The books

**Stripe holds the transactions; MySet produces the statements.** Every figure comes from
Stripe's **balance transactions** — the list Stripe itself reconciles to the bank — and is
only bucketed, never recomputed. A second ledger that re-derives what a charge was is a
machine for disagreeing with Stripe.

- **Artists** — Studio → Money → *Your earnings*. Twelve months, gross / fees / net, plus
  a CSV for the tax return. The first month is **the month they joined**, not a year of
  zeros.
- **Venues** — the same, scoped to the venue's own account. Venues had nothing before
  this.
- **Perry only** — *MySet's books*: a real P&L, revenue read from Stripe, costs typed in
  by hand, profit = net − spend. Owner-only **on the server**, not merely hidden in the
  page.

A finished month is computed once and cached, so a year's statement costs one Stripe page.
Two traps pinned by tests: Stripe's fee comes from `fee_details`, **never** `bt.fee`
(which on a direct charge contains ours too); and **a payout is not an expense**.

**The founder's own gig money is separable after all** — by *tag*, not by account.
`platformSplit()` buckets every platform balance transaction into *his gigs* or *the
company* using the `kind` and `artist` metadata that `pay.mjs` now writes onto every
payment intent. Without that, a "Your earnings" card built on his balance would read other
artists' subscription payments back to him as income.

Full reasoning: `ACCOUNTING.md`.

## 4.6 Featured shows

**$10 puts one gig at the top of that city's list for that night. Three spots per city per
night, first come first served**, orange border, own heading. Behind the `featuredShows`
flag; with it off there is no button, the endpoint refuses (so nobody can be charged), the
section is not drawn, and **anything already bought keeps its record** and reappears when
it is switched back on.

The hard part was never the payment, it was the race. **A twenty-minute hold** is taken
inside a compare-and-set, keyed by an id MySet mints and carries **through Stripe's
metadata and back** — so nobody is ever charged for a spot they did not get, and an
abandoned checkout frees it by itself. A payment that lands after the hold died is honoured
if there is room and **refunded automatically** if there is not, once, keyed by the session
id; a refund leaves a tombstone the other settle path refuses to grant against, and the
tombstone lives as long as the night.

Two of the bugs an adversarial review found here are worth carrying to any similar feature:

- **A rival could stand in a paid spot.** The city feed matched a featured row on
  `eventId` alone, and event ids are chosen by the *client* and public in that very feed.
  Now matched on the owner as well, with the internal owner id stripped before the payload
  goes out.
- **The garbage collector pruned on the calling artist's local date** inside a *shared*
  city table — so an artist in Bangkok could have deleted a London artist's **paid** row
  for a night London had not reached. The delete floor is now two days behind UTC. **A
  local date is fine for deciding what to show and never for deciding what to remove.**

## 4.7 Artist discovery and one global theme

Home links to a public `/artists` directory. It searches names and profile copy, filters
by country/city using upcoming public gigs, and can narrow to artists with upcoming shows
or released music. Released music means a public Spotify, Apple Music or YouTube Music
link, or linked label/management attribution. The directory never exports registry email,
role or billing fields and its API is explicitly `no-store`.

Light/dark is one persisted browser choice across public pages, Artist Studio and Venue
Studio. Each page exposes the same compact control; the shared script owns its state and
both Studios provide explicit light palettes rather than assuming a dark stage screen.

# PART 5 — HOW IT IS BUILT

## 5.1 The shape

Static HTML pages plus **Netlify Functions** on **Netlify Blobs**. No framework, no build
step, no database. Every page is one self-contained file with its own styles and script;
`app.css` carries the shared design tokens and is **not** loaded by either Studio.

**Two dependencies only:** `@netlify/blobs` and `stripe`.

Counts are generated in §2.1.

## 5.2 Storage

Netlify Blobs, one store, everything namespaced per artist or venue.

**Per artist:** `show_` · `f0…f11_` (fan records, sharded) · `meta_` (payments and tips) ·
`hist_` / `histidx_` / `histids_` / `histpend_` (past shows) · `ev_` (gigs) · `lists_` ·
`learn_` · `req_` · `profile_` (merch lives on it) · `img_` · `chart_` · `lyr_` · `push_` ·
`connect_` · `fb_` · `lock_` · `apitch_` · `songstats_` · `posts_` / `likes_` ·
`billing_` · `ledger_` · `vidpend_`

**Per venue:** `v_` · `vprofile_` · `vouch_` · `vpitch_` · `posts_v_` · `likes_v_`

**Global — the only shared documents:** `artists` (the registry) · `venues` · `cityindex` ·
`acctindex` · `flags` · `idqueue` · `promos` · `authsecret` · `authc_` · `sheetsync` ·
`gigsched` · `vidqueue`

### The five hard-won storage rules

1. **Never use `list()` for live data.** It is eventually consistent and has been measured
   lagging by *minutes*. Vote counts read that way showed zero while the writes had
   already landed. **Every key must be computable** — which is why every collection has an
   index document.
2. **`list({ prefix })` returns nothing if the prefix cuts inside a nested `a/b/` path.**
   Keys that need prefix listing must be flat.
3. **Conditional writes need `@netlify/blobs` v10+.** v8 accepted them and silently
   ignored them, and votes were lost. Do not downgrade.
4. **Compare-and-swap alone is not enough.** Even on v10 a conditional write can report
   success without sticking. Every fan write is **re-read after writing** and retried.
5. **Fan records are sharded across 12 documents** so a burst of voters does not contend
   on one key. Load-tested: 80 simultaneous voters, zero loss.

Decision record [`0008`](docs/decisions/0008-never-list-blobs-for-live-data.md).

## 5.3 What an endpoint costs

Counted **by a test**, because reads on the audience poll are the mistake this project
keeps making — the global registry got onto that path three separate times.

| | Ceiling |
|---|---|
| The shared board (`/api/board`) — rendered **once per polling interval for the whole room** from 201 phones, served from the edge in between | **15** reads, **1** global document |
| The personal call (`/api/me`) — every phone, every tick | **3** reads, **one** fan shard, no global document on the founding page, **no write** once present |
| The old audience poll (`/api/show`, kept for pages opened before the split) | 15 reads, 1 global document |
| A vote | 5 reads, 2 writes |
| Studio poll | 22 reads |
| A setlist rename | 12 reads, and **no** fan-shard reads |

These are ceilings, not targets. Raising one is a decision somebody makes on purpose and
explains, **not something discovered on a bill**. Since 2026-09-11 the audience poll is
two calls (decision [`0034`](docs/decisions/0034-the-audience-poll-is-split-into-a-shared-edge-cach.md)):
the expensive half is paid once per interval for everybody, and the half every phone pays
reads a twelfth of the room instead of all of it.

## 5.4 Polling

The audience page polls at the interval the **server** sets (§1.12), backing off two rungs
when nothing is changing, with **±20% jitter** and a terminal rung, and stopping entirely
when the phone is asleep or the tab is hidden — so a pocketed phone costs nothing. The
Studio's Live tab polls every 4 seconds.

**`signature()` used to include the total vote count**, so any cast by anybody reset every
phone in the room to the fastest rung and the slower rungs were unreachable in a busy room.
It is now split into `stageSig()` and `signature()`, with the room's size deciding which
drives the ladder — below the server's widening point nothing changes at all, because at
eight people the tally jumping the instant somebody votes **is** the product. That one
split took a 10,000-person gig from $36.40 to **$4.29**.

## 5.5 Sign-in

**The audience never signs in.** That is why the app works in a bar.

**Artists** sign in with **email and a 6-digit code** — not Google, because OAuth needs a
cloud project, a consent screen and a verification review. Codes last ten minutes, are
burned on use, and allow five wrong guesses and five sends per hour. Artists may also set
a **Studio passcode**, used with their page name — the pair behaves like a username and
password: at least 8 characters, a deny-list, and the door locks for 15 minutes after 10
failures. **A locked door, a wrong code and an unknown page name all give the same
answer**, so the lock cannot be used to discover which codes or artists are real.

**Passkeys** are built, with no npm dependency — WebAuthn verification is SHA-256, a
signature check, base64url and enough CBOR to read two maps, all of which Node does. *A
dependency in the sign-in path is a dependency that can be taken over.* The Face ID button
appears only once that browser has signed in at least once, because a passkey belongs to a
page and the sign-in screen does not yet know which page you are. `test/passkeys.mjs` acts
as a **real authenticator** — real P-256 key pair, real attestation object, real signature
— and defeats each of the five checks on purpose. The subtle assertion: a synced iCloud
passkey reports a counter of zero for ever, so refusing on "not greater" would lock out
exactly the devices this exists for.

**Roles.** `owner` runs everything. `member` runs the page and the show and never touches
money or access. `crew` runs tonight and nothing else — the sound engineer working the
screen while the artist plays. **An unknown role falls back to `crew`**, so a role string
the table has never heard of can never be an escalation. Venues have the same three, named
owner / manager / crew.

**Sessions.** Every token carries a session id, so one phone can be signed out without
signing out the band. Revocation lives on the registry row the verifier is already reading
and is normally absent, so it costs nothing on any request.

**Recovery.** Eight one-time codes, shown once. Using one **signs out every other device**.
A wrong code, an unknown page and a locked-out page all answer identically.

**MySet has no password**, and Settings says so plainly rather than leaving somebody
hunting for a "forgot password" link that could not exist.

## 5.6 Verification and the tick

**A venue** needs five things: a paid plan, a website on its page, the sign-in email on
that website's domain, the website naming the venue, and **3 different artists who have a
gig listed there** confirming it.

**An artist** needs a paid plan, card payments actually working, and a photo of an ID
submitted with their **full legal name and date of birth**.

**Most artists are verified instantly, with no human involved.** Setting up card payments
means Stripe has already run a real identity check. So the upload compares the stated legal
name and date of birth against the ones Stripe verified; if the name matches (same names,
or the same plus a middle name) and the birth date matches to the day, the tick is granted
on the spot. Anything less goes to Perry with the comparison written on the row.

- **It asks for the LEGAL name, not the page name.** Perry's page says Idyll; his passport
  says Murdaugh. Comparing display names would have failed for most real people.
- **The date of birth is compared once and thrown away.** Only the yes/no is kept, and a
  test asserts the stored row does not contain the date.
- **Nothing reads the photo.** No text extraction, no face comparison. The automatic path
  leans entirely on Stripe's own KYC, and this is stated wherever the feature appears —
  **a badge that claims more than it checks is worse than no badge.**
- **The ID photo is never public and never kept.** It goes to a slot the image endpoint
  refuses to serve, and is deleted the moment a decision is made either way.
- **Paying opens the door to being checked — it never buys the tick.**

## 5.7 Shows that start and end themselves

A gig on the calendar **starts its show at the gig's start time** if the artist hasn't
already, and **ends it three hours after the gig's scheduled end** if the artist hasn't.

`_lifecycle.mjs` is the **one** implementation of starting and ending — the Studio's
buttons and the scheduler call the same two functions, so the gig cap, the archive,
tonight's setlist, the venue name and the paid-vote carry happen identically whoever asked.
`_auto.mjs` decides; `autocron.mjs` rings every two minutes and reads **one** global
document, `gigsched`, that every calendar write keeps current — so a quiet ring costs one
read and **the audience poll is never touched**.

What it will not do: start the same gig twice; restart a night the artist ended themselves;
start a show with no songs switched on; end a show while a song started in the last 45
minutes; start a venue's own event; retry a cap refusal all night. **A night where nothing
happened — no song, no vote, no phone — is not archived**, so an empty scheduled start
never becomes "Shows: 1".

**Nine ways a night could vanish were closed on 2026-09-05**, and the shape of them is
worth knowing: a Stripe hiccup that threw past the archive into an empty catch; an index
row built from the wrong snapshot; two writes that both ended in `.catch(() => {})`; a
`status === 'pre'` guard that made every later archive return null for ever; an index cap
of 100 that stranded row 101 invisibly; and a browser cache that was never invalidated, so
ending a show made the night **look** lost. There is now a **heal** that rebuilds an
artist's index from every id it can name, behind a "Look for missing shows" button.

## 5.8 Everything else

**Lyrics** come from LRCLIB — free, no key, no AI — fetched by the **server** (the browser
cannot set the header LRCLIB requires) and cached permanently. Labelled *"Unofficial
lyrics"*, current song only, one-tap removal.

**QR codes** are generated as SVG by a hand-written encoder (`_qr.mjs`), with the **MySet
mark in the centre**. Two things learned there and pinned by `test/qr.mjs`:

- **The badge is 17% of the width.** Level M rebuilds about 15% of a code. Rendered and
  decoded 15 real codes at three scales under downscale and blur: at 21% three of fifteen
  stopped reading; at **17% all fifteen read, identical to a plain code**.
- **The dark module bug.** Every QR code has a permanently black module at
  `(4×version + 9, 8)`. The writer treated it as format bit 7, writing the bit there and
  shifting the whole top-right run of the **second** format copy by one. The top-left copy
  was still correct, so readers fell back to it and **39 of 40 codes scanned anyway** — which
  is why it survived a module-for-module review. There was no QR test at all before
  2026-09-07, for something that gets printed and stuck on tables.

**Photos** are shrunk on the phone before upload and checked on the server. **Photo slots
are addresses**, not a list: both normalisers used to `.filter(Boolean)`, which compacted
the array, so a venue with slots 1 and 3 filled had slot 3's picture drawn in slot 2. Only
trailing blanks are dropped now.

**Embeds** accept YouTube, Spotify and Apple Music only. A pasted URL is a **parse input**,
never stored raw and never used directly as a frame source.

**Push alerts** were written from the specification by hand with no new dependency and
checked against the specification's own published test vector. **The keys are not set on
the server, so they cannot send yet**, and the Studio says so.

**Installable.** Three separate manifests (audience, Studio, venue) so each surface opens
where it should. The service worker **never caches anything under `/api`** — a cached vote
is a lost vote — and never precaches, so the newest version always wins.

**Feature flags** let a question with two real answers be tried both ways without a deploy
(a production deploy is the expensive thing on this account). Rules: a flag is a question
with **two real answers, both of which work** — never a way to ship something
half-finished; every flag is listed in `FLAGS` with what "off" means; flags are read on the
hot poll so the document is cached in module scope for 60 seconds and **never written
during a show**; and **every flag needs a removal plan written into its own description**.
`voteFinal` lived there from 2026-09-02 to 2026-09-07 and is gone rather than left sitting
on its winning answer — which is the system working.

**Time** is handled without a library: a gig is a wall clock in a named place, stored as a
date, a time and an IANA timezone. **A set running past midnight belongs to the night it
started.**

**Pull to refresh** — one implementation, `public/pull.js`, on every page. Installed to a
home screen there is no address bar, no reload button and on iOS no swipe-down gesture, so
a stale page had no way out except force-quitting. It arms only within 2px of the top,
every listener is passive, it stands down while any sheet is open, and the browser's own
gesture is deliberately **not** suppressed. It is JavaScript, so it cannot rescue a page
whose JavaScript is broken — that is what the two buttons under **Settings → If something
looks wrong** are for.

**The Google Sheet** is a nine-tab export for marketing and for working out which songs a
room actually wants. `GOOGLE-SHEET-SETUP.md` is the walk-through. The ten rules that make
it safe are worth reading before building anything similar; the four that generalise are:
**it is a copy, never the source**; **off until three env vars exist, and off is a clean
no-op with a reason**; **a cap defers, it never drops**; and **formula-shaped text is
escaped**, because a song called `=1+1` and an artist called `+Plus Band` are both real and
Sheets runs both.

# PART 6 — RUNNING IT

## 6.1 Deploying

```bash
cd ~/Docs/MySet && sh test/run.sh
git switch -c <area>/<what-changed> && ./tools/pushlog.sh "what changed" "note" && git push -u origin HEAD
gh pr create --fill && gh pr merge --squash --delete-branch
```

Merging a pull request into `main` **is** the production deploy. Since 2026-09-12 `main`
is protected by a GitHub ruleset (decision 0045): direct pushes are refused, force-pushes
and deletion are blocked, a PR needs no approvals — the person shipping merges their own —
and every PR gets a free Netlify deploy preview on the exact bytes that will ship. **Never
also run `netlify deploy --prod`** — that bills a second deploy for the same change and
races over what is actually live (INVARIANT 9d3).

**Only `public/` is published.** Publishing the repo root once exposed docs, backups and
the design handoff on the live domain.

**Verify by CONTENT, never by status code.** A catch-all slug redirect answers 200 for
files that do not exist, so `curl -w %{http_code}` has already reported a deploy as landed
mid-build. Fetch the page and grep for the thing you changed.

## 6.2 What it costs to run

Netlify bills in **credits**: 2 per 10,000 web requests · 20 per GB of bandwidth · 10 per
GB-hour of compute · **15 per production deploy**.

| | |
|---|---|
| A 3-hour gig, 20 people | **2.7¢** |
| A 3-hour gig, 1,000 people | $0.98 |
| A 3-hour gig, 10,000 people | **$4.29** (was $36.40 before the signature split) |
| At 10,000 artists | ~5.6% of revenue, **and the ratio does not move with scale** |

**Production deploys are the expensive thing, not traffic.** Measured over three weeks:
1,697 credits, **99% of it deploys**, 17 credits of traffic. Deploys ran **29× the cost of
every gig played**, and ~570 credits of that were the same change shipped twice (CLI plus
the GitHub build the same push triggers).

**Never re-derive cost from response times.** That has been got wrong three times.

**Two counterintuitive findings, both verified against published rates:**

- **Moving to Cloudflare Workers + KV would be worse**, not better, because KV bills per
  read and MySet does ~90,000 reads a gig. The platform is not the cost driver; **fifteen
  reads per poll is**.
- **A cache header on `/api/show` saves nothing.** The poll URL carries `fan=<id>`
  and production returns `netlify-vary: query`, so 10,000 phones make 10,000 cache keys —
  and **Netlify bills a web request for a cache hit**. Caching would remove compute only:
  63% at best, **0% as that endpoint stands**. This was the recommendation in the first
  version of the cost report and would have been a day spent for nothing. **The split
  (live 2026-09-11) is the version that works**: `/api/board` has no fan id and is held at
  the edge for the polling interval, `/api/me` is tiny and never cached. Money barely
  moves — a 20-person gig goes from 2.7¢ to 3–4¢ because every tick is now two requests
  and a cache hit is still a request; 1,000 phones go from $0.98 to $0.56, 10,000 from
  $4.29 to $3.76 — but the store's read traffic per phone is a twelfth of what it was.
  At the record size the room-ceiling report assumed, the busiest case at 10,000 falls
  from 462 MB/s to 40 MB/s; at the record size the vote path actually writes today
  (~2 KB for a fan who cast eight times), the busiest-case wall moves from
  **~700–1,000 people to ~2,500** (`tools/loadsim.py --ceiling`). Reads were the wall,
  not money — and the old ~2,500 was already optimistic, because a voter's record has
  grown since it was written. One rule the live edge taught: **Netlify's durable cache
  ignores a lifetime under 10 seconds**, so the polling dial has no 5-second rung any
  more — pubs keep 3 s with a per-node copy, and from 201 phones it is 10 s, shared.

The one thing that can move the bill on its own is **clips** (§3.7). Cloudflare R2 —
$0.015/GB-month to store, **$0 to serve** — is the answer when they take off. **Trigger:
about 100GB of clip traffic a month (~$13).**

## 6.3 Secrets

Never in the repo, never in a chat window. All set by Perry directly in Netlify:

`ADMIN_CODE` · `STRIPE_SECRET_KEY` · `STRIPE_WEBHOOK_SECRET` · `RESEND_API_KEY` ·
`VAPID_PUBLIC_KEY` · `VAPID_PRIVATE_KEY` · `VAPID_SUBJECT` · `AUTH_FROM` ·
`SPOTIFY_CLIENT_ID` · `SPOTIFY_CLIENT_SECRET` · `GSHEET_ID` · `GSHEET_EMAIL` · `GSHEET_KEY`

**Four are set in production**: `ADMIN_CODE`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`,
`RESEND_API_KEY`. Everything else is unset, and each **degrades honestly rather than
failing** — push alerts say they cannot send, the Sheet is off, Spotify import answers an
honest 503, and sign-in refuses to claim success until `AUTH_FROM` names a verified,
non-sandbox sender.

**A Netlify env var marked secret is unreadable through the API** — it returns a
placeholder, not the value. That is correct behaviour and it has already caused one false
diagnosis: a masked `ADMIN_CODE` was sent to the admin door, correctly refused, and
reported as *"the recovery key is broken"*. It is not broken; it is unreadable by design.
**Do not repeat that conclusion.**

## 6.4 Testing

```bash
sh test/run.sh              # the whole suite; counts are in §2.1
node tools/overview.mjs --tests   # run it and stamp the count into this document
```

The suites run the **real handlers** against an in-memory store that implements the same
etag behaviour as the real one, injected by a module hook. Stripe is stubbed the same way,
and **the stub records the options of every call** — which is how a direct charge is
*proved* to be direct.

**A test double that is more permissive than the real thing is a test that passes for the
wrong reason.** The Stripe fake's `checkout.sessions.list` once ignored the `created`
window, so every session was visible in every query — which is exactly why no test could
catch a lookup that only reached back one month.

**Three things no node test can see**, each with its own browser tool:

| Tool | What it proves |
|---|---|
| `node tools/sheetcheck.mjs` | bottom-sheet touch behaviour, with **real TouchEvents** at a 390px iPhone viewport |
| `node tools/uicheck.mjs` | rendered layout — the last-call box pinned without reflow, the dock surviving the end of a show, the ring on one button and not the other, link order as rendered |
| `node tools/clipcheck.mjs` | that the uploaded pieces **are the file, byte for byte**, and that the sound is still in it |

## 6.5 Before shipping anything

1. Read the invariants for whatever you are touching.
2. `sh test/run.sh`.
3. **Look at it in a real browser.** Several defects a month are invisible to the tests and
   obvious on screen.
4. Push, then **verify from outside** by content.
5. Write the decision record if the change could have gone another way (Part 7).

# PART 7 — HOW THIS DOCUMENT STAYS TRUE

*Added 2026-09-08, at Perry's request: "implement a system that AUTOMATICALLY updates this
file when new changes are made… we need a report for every single engineering decision made
with reasoning for why that decision was made."*

There are two halves, and they fail differently, so they are solved differently.

## 7.1 The numbers update themselves

Documents do not usually go stale in their prose — somebody rewrites that when the product
changes. They go stale in their **numbers**: a price, a cap, a cut, how many endpoints there
are, how many assertions passed. And a wrong number is worse than no number, because a
reader who checks one and finds it right trusts the next fifty.

So **§2.1 is generated**, and the prose around it never repeats a number it does not own.
The plan table is not a copy of `PLANS` — it *is* `PLANS`, rendered.

```bash
node tools/overview.mjs            # regenerate §2.1 and the decision index
node tools/overview.mjs --check    # exit 1 if either is stale
node tools/overview.mjs --json     # every generated fact, as data
node tools/overview.mjs --tests    # run the suite and stamp the assertion count
```

**It runs on every commit.** `tools/hooks/pre-commit` regenerates the block and stages it.
Install once per clone:

```bash
./tools/hooks/install.sh
```

**The hook never blocks a commit.** `main` is production and this repo gets edited between
sets; a hook that refuses a commit at 11pm because a document is out of date is a hook
somebody disables with `--no-verify` and never re-enables. So it fixes what it can, says
what it cannot, and gets out of the way.

## 7.2 Every decision gets a record

`docs/decisions/` holds one file per decision, in a fixed shape, with front-matter a machine
can read.

```bash
./tools/decide.sh "what is now true"      # scaffolds the next one
```

Each record answers six things, and the second is the one most decision logs skip:

1. **The question** — and what forced it
2. **The options** — *every* one that was genuinely on the table, in a table with **what it
   costs, what new moving parts it introduces, and what the risk is if it goes wrong**.
   **"Do nothing" is in the table every time**, because it is always available and sometimes
   right; a comparison that omits it is a justification, not a decision.
3. **What was chosen, and why** — the reason, not a restatement. *"Perry said so"* is a
   legitimate and common reason here, and writing it tells a future reader not to argue.
4. **What this makes harder** — every decision closes something off. Name it now, while it
   is still obvious.
5. **What would reverse it** — the condition under which to revisit. **A decision with no
   reversal condition is one nobody can safely revisit.**
6. **How it was verified** — what was actually run and what it printed. "Tests pass" is not
   verification.

**What is owed a record:** anything that changes what a person can do, is charged, or is
told; anything that adds a moving part; anything that closes off a future option; any number
somebody could argue with; and any reversal of an earlier decision — which **supersedes**
rather than deletes it.

**What is not:** refactors that change no behaviour, copy fixes, tests for existing rules.

**Nothing gets lost.** `tools/hooks/post-commit` writes any commit that changed
`netlify/functions/` without a decision record into `docs/decisions/PENDING.md`. It is a
backlog, not an accusation — but a decision nobody writes down is one nobody can revisit.

The index, `docs/decisions/README.md`, is generated from the front-matter. **Edit the
records, never the index.**

## 7.3 What this system does not do

- **It cannot know whether the prose is still true.** It checks numbers, not claims. The
  landing-page audit on 2026-09-06 found **69 upheld contradictions** between the sales page
  and the app, and no generator would have caught one of them — that took reading both and
  comparing. Prose is still a human job.
- **It cannot write the reasoning for you.** The hook can tell you a record is owed; only
  the person who made the decision knows what the other options were.
- **The seeded records are the important dozen, not all of them.** Everything before
  2026-09-08 lives in `INVARIANTS.md` (every property, most with the story of how it was
  found) and `docs/sessions/`. The decision folder is complete **from 2026-09-08 forward**.

# PART 8 — WHAT IS NOT DONE

- **Four Pro features are sold in the plan copy and not built** — `promote`, `analytics`,
  `presskit`, `branding`. They are named in `NOT_BUILT` and shown as *"Coming soon"* on

- **Venue tips and venue speaker-voting** — same treatment on the venue ladder.
- **Venue merch cannot be bought through MySet** where the venue has no payout account;
  those items sell through the venue's own link, and the Venue Studio says so.
- **Videos on community posts are links, not uploads** (clips are a separate thing and are
  uploads).
- **No off-switch for scheduled starts per gig.** A gig on the calendar starts its show and
  the artist can end it; a per-gig *"don't start by itself"* is the obvious next knob.
- **Push alerts cannot send** — `VAPID_*` are not set on the server.
- **Spotify playlist import cannot run** — `SPOTIFY_CLIENT_ID` / `_SECRET` are not set. The
  button is offered and answers an honest 503. **This is the one place the artist is shown a
  control that leads to a message rather than a result.**
- **Public sign-in email is unavailable** because `AUTH_FROM` is unset. Resend's former
  `onboarding@resend.dev` fallback can send only to the Resend account owner, so MySet now
  fails closed instead of telling a stranger that an undeliverable code was sent. Verify
  the MySet domain in Resend and configure a sender on it.
- **Payout countries are a 22-country list**, not Stripe's full set. Deliberate: the
  alternative was accepting any two letters and creating an account in the wrong country,
  permanently.
- **A deploy preview shares production data.** The money half is closed — Stripe keys are
  unset for preview contexts — but a preview can still **write** real data. Use previews to
  look at pages, never to exercise a write path.
- **The shared-board split is live** (2026-09-11, `c3d0a4d`): one cacheable board with no
  `fan=` plus a tiny per-fan call — decision
  [`0034`](docs/decisions/0034-the-audience-poll-is-split-into-a-shared-edge-cach.md).
  The plan's audience numbers are **not** raised: the ceiling moved in a simulator, the
  write wall has never been measured, and a fan's record turned out to weigh ~2 KB after
  eight casts (the cast receipts), which the earlier ceiling did not know.
- **An open line to the room is researched and deliberately not next** — decision
  [`0012`](docs/decisions/0012-an-open-line-to-the-room-is-not-next.md).
- **Cloudflare R2 for clip bytes** — designed, not built, needs Perry's own Cloudflare
  account. Trigger: ~100GB of clip traffic a month.
- **Nobody has tested a restore, nobody is alerted when something breaks, and there is no
  written plan for a bad day.** `SECURITY.md` says this plainly: **the gap between MySet and
  a grown-up SaaS is process, not code.**
