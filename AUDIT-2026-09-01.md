## C001 — One failed background poll throws the artist out to the sign-in screen mid-gig and permanently stops the live refresh

**CONFIRMED** · severity **high** · impact **breaks-a-live-gig** · breaks INVARIANT 16

*Reported independently by 3 lens(es): Bar wifi, locked phones, and the service, completeness-critic, public/studio.html — the Studio as the a*

**What was run**

```
Concatenated VERBATIM `sed -n '706,790p'` (busy/api/load/act/gate/unlock) + `sed -n '2296,2297p'` (start) from public/studio.html with a stub DOM/localStorage/fetch prelude into /tmp/c001/probe.mjs; `node probe.mjs`. Case A fetch rejects TypeError('Failed to fetch'), Case B 502 whose r.json() throws. Both: poll1 -> `#app`=Studio, timer alive. poll2 (one failure) -> `#app`=`<div class="gate">…Sign in to run your show.`, timerAlive:false, token still 'TOKEN-ABC'. 4.3 s later with fetch healthy again: still gated, timer still dead. probe2.mjs: a failed `act()` only toasts and keeps the screen.
```

**Why it stands**

Code matches the quotation. api() (715-726) collapses every transport/parse failure into {ok:false,error:'Connection hiccup — try again'}; load() (728-732) treats any !ok as an auth failure and calls gate(), which clearInterval(timer)s and overwrites #app. No guard exists anywhere in the chain: sw.js rule 1 never caches /api, there is no online/visibilitychange listener (grepped: zero), and stage.mjs's only non-ok answer is bad('unauthorized',401). Mitigation the auditor understated: the token is NOT cleared (error string isn't 'unauthorized'), so a reload — or a tap on "Unlock with code" with an empty box, which I verified restores the Studio — recovers it once network returns. It violates INVARIANT 16 ("no error state should block the page from rendering") and act() at :743 already does the right thing with the same api(), so this is an inconsistency, not a decision.

**Correction to the original report**

Two corrections to the report. (1) The token is NOT lost — only 'unauthorized' clears localStorage, so a reload restores the Studio with no re-auth; the artist is confused, not locked out. That is why this is high and not catastrophic. (2) venue-studio.html has NO setInterval anywhere (grepped), so its copy fires only on a user-initiated action: low severity, not "less severe" on the same scale.

**Smallest correct fix**

Two lines in public/studio.html. In api()'s catch (725): `return {ok:false,offline:true,error:'Connection hiccup — try again'};`. In load() (729), first line of the !d.ok branch: `if(d.offline&&D){ return; }` — keep the last good screen and let the still-running 4 s interval retry. Keep the `&&D` guard: on the very first load with no state, gating is still the right answer, and dropping it would leave #app blank. Do NOT adopt the sketch's "clearInterval only on unauthorized" phrasing without it.

**PARTLY** · severity **high** · impact **breaks-a-live-gig**

**What was run**


TWO STATED HARMS REFUTED by measurement:

Head-count. `clearAllFanVotes` runs on every song start, so bot records stop satisfying `roomCounts`' `here` test — room went 1540→40 at the next song, and the archive stored `room: 40`, not 2040. `_vstats.mjs:53` reads `s.room`, so the venue's people figure is clean. Also: `nets` stays 1 (INVARIANT 0ae keeps it precisely as this defence) and stage.mjs:46 shows it, so "1540 phones / 1 network" is on the artist's screen; `resetVotes` fully restores queue and head-count.

**Smallest correct fix**

## C028 — Bought vote packs never deplete — `extra` is a permanent per-round allowance, so one $3 purchase buys unlimited voting for the whole night and every night after

**CONFIRMED** · severity **high** · impact **loses-money**

*Reported independently by 1 lens(es): Vote & credit accounting — every path th*

**What was run**

```
/tmp/c028/probe.mjs + probe2.mjs via `node --import test/register.mjs`, real admin/show/vote handlers + real `redeemSession` grant.
Probe 1 (freeCredits=1, 3-vote pack): 5 rounds, each `playTop`. Every round `cast 4 votes | {"remaining":0,"total":4,"used":4,"extra":3}` = 20 votes. Then `newShow` → `{"total":4,...,"paidLeft":3}`, 3 more rounds = 12 more. 32 votes, still `extra:3`.
Probe 2 (default freeCredits=3): fan spends all 6, artist taps `newShow` → fan record `undefined`, next show `{"total":3,"extra":0,"paidLeft":0}`.
```

**Why it stands**

No guard exists. `total` is derived fresh at _lib.mjs:401, show.mjs:23, vote.mjs:41, _requests.mjs:93 as `freeCredits + extra`; `creditsUsed` counts only `me.v` + `me.spent`, both zeroed by `clearAllFanVotes` (_lib.mjs:383-390). Nothing but gift.mjs:26 ever decrements `extra`. Not an intentional decision: no INVARIANT covers it, MYSET.md:130 says only *free* credits refresh, MYSET.md:139 and gift.mjs's own header talk about "votes they paid for but never spent", and `unspentPaid`'s comment says paid votes "carry into the next show" — a design that assumes spending depletes them. The clearAllFanVotes comment shows the author reasoned about `spent` being charged against free credits and simply never split the paid portion out.

**Correction to the original report**

One detail in the failure scenario is narrower than claimed: the carry is not unconditional. `unspentPaid` returns `extra` only when the fan isn't spent-out at the reset instant. If they are (probe 2), `carryFans` computes 0, `delete bag[id]` fires, and the paid pack is destroyed — the opposite bug, from the same missing ledger, and the one that actually angers a paying customer. Both must be fixed together.

**Smallest correct fix**

Derive, don't ledger. Add `paidRound(fan,show)=max(0,creditsUsed(fan,show)-show.freeCredits)` (free is always consumed first, so it needs no storage). Persist only `fan.paidUsed`: `total = freeCredits + extra - paidUsed` (4 call sites); `unspentPaid = max(0, extra - paidUsed - paidRound)`; `clearAllFanVotes(aid, show)` folds `paidRound` into `paidUsed` before clearing; `carryFans` writes `extra: unspentPaid, paidUsed: 0`.

## C051 — Purchased votes are never consumed — a $11 pack grants +18 credits EVERY round for the rest of the night, and `unspentPaid`/`carryFans` assume the opposite

**CONFIRMED** · severity **high** · impact **loses-money**

*Reported independently by 1 lens(es): Design Question 2 — un-voting, vote "was*

**What was run**

```
Copied repo to /tmp/c051/repo, wrote 5 probes run with `node --import test/register.mjs`.
probe.mjs (real handlers, real `redeemSession` money path, votes:18, freeCredits:3): after purchase remaining=21/21; cast 6 → 15/21; `admin play` → **remaining=21/21, extra=18**; 12 more rounds → sum of per-round totals = 252.
probe2.mjs: 3 shows × 3 heavy rounds + `newShow` each → extra stays 18 forever.
probe3.mjs: 25 songs, spend all 21 in one round, then `newShow` → fan record deleted, 18 paid votes gone.
probe4/5.mjs: my fix applied to the copy → 18 paid votes consume over 5 rounds then back to 3/round; un-vote refund intact. unit+e2e+tenancy = 110 assertions pass.
```

**Why it stands**

Not an invariant. INVARIANT 14 covers free credits ("each round is a fresh contest"); nothing documents `extra` as a night pass, and the whole paid path is written as a stock: pay.mjs sells "18 extra votes… for tonight's setlist", `unspentPaid`/`carryFans` compute leftovers, gift.mjs debits, and vote.html says "You've got N votes left… keep them for the next show". No guard exists anywhere — `extra` is only ever read as part of `total`, and decremented in exactly one place (gift.mjs:26). Confirmed the auditor's exact numbers, plus two things they missed: (1) `extra` survives `newShow` untouched, so one $11 pack is 21 credits/round at *every future gig* of that artist, permanently; (2) the mirror case — `unspentPaid` is the only place the stock model is ever applied, so a fan mid-spend at `newShow` silently loses `used - freeCredits` paid votes, and a fully-spent round loses all 18. Reachable on the paid happy path with no artist action.

**Correction to the original report**

The auditor's fix sketch is wrong in two ways. Debiting `extra` in the vote.mjs cast branch double-charges — `creditsUsed` already counts the vote while `total` would shrink — and it breaks INVARIANT 15 unless the un-vote branch re-credits `extra`, which the sketch omits, so toggling a vote off would burn a paid vote. Mirroring it in _requests.mjs:93 is also unnecessary: requests charge `me.spent`, which `clearAllFanVotes` already zeroes, so a settle-at-reset fix covers them with no change there. Settling once at the round boundary needs no edit to vote.mjs or _requests.mjs at all.

**Smallest correct fix**

Settle at the round reset, not at cast. In `clearAllFanVotes(aid, costShow)`, before zeroing each fan: `const paid = Math.max(0, creditsUsed(f, costShow) - (costShow.freeCredits||0)); if (paid>0) f.extra = Math.max(0, (f.extra||0) - paid);` and in admin.mjs snapshot `preShow = await getShow(aid)` in the existing play/playTop block, passing it at line 1053 (played[] has already moved by then, so the just-won replay would otherwise be charged 1 instead of replayCost). Verified: consumes 18 over 5 rounds, 110 existing assertions still pass.

**Correction to the original report**

Two details in the scenario are wrong. (2) The audience is untouched — show.mjs and vote.mjs call no auth at all, so voting continues; what dies is the artist's control panel (stage/admin), not the show.

**Smallest correct fix**

Per-artist rev, with a fallback so the fix itself doesn't sign everyone out. _auth.mjs verifyToken: move the `link` lookup ABOVE the rev check, then `if (String(reg.byId[link.artistId].rev ?? reg.rev) !== String(rev)) return null;`. auth.mjs:64,85: sign `reg.byId[link.artistId].rev ?? reg.rev`. auth.mjs:123: `const m=a.byId[me.aid]; m.rev=(m.rev ?? a.rev ?? 1)+1;`. Mirror in _venues.mjs/venueauth.mjs.

The auditor's sketch is wrong on one point: bare `byId[aid].rev` with no `?? reg.rev` is `undefined` on every existing record, so deploying it 401s the whole platform once — it fires the bug it fixes. Keep global rev as an extra kill switch only if checked additionally, and reword INVARIANT 9i.
