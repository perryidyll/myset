Why this came up

A ten-second countdown made the limit visible

The artist taps Last call. A box appears at the top of every phone in the room counting down from ten. Except it does not — it appears on a phone the next time that phone happens to check in.

In a small room that is every three seconds, so nearly everyone sees it. In a big room the interval is deliberately longer, so some phones never see it at all. The countdown is a nudge and does not have to reach everyone to do its job — but it is the first feature where the app knew something the room did not, and had no way to say so.

That is what an open line fixes. Instead of ten thousand phones asking "anything new?" every few seconds, the server says "here" once, and everybody has it.

Server work stops being people × time and becomes events.

The blocker

Netlify cannot hold a line open, and it is not a setting

A Netlify Function is: request in, response out, gone. There is no process left alive afterwards to hold a socket.

This is true of serverless hosting generally, not a Netlify shortcoming — their own writing on realtime points you at a third party for exactly this reason. There is no plan, no flag and no configuration that changes it.

So an open line means a second platform running alongside Netlify. That is the real cost of this feature, and it is not measured in dollars. It is a second place things can break, a second deploy pipeline, a second bill, a second set of credentials, and a fallback path that has to be maintained forever because it will be used.

The mechanism

How Cloudflare actually works, in plain words

The thing that makes Cloudflare right for MySet is not that it is cheap. It is that its billing shape happens to match the product's shape exactly.

A Durable Object is a tiny computer per show

Normally, serverless code has no memory — every request starts from nothing and has to look everything up. A Durable Object is the opposite: it is a small program that stays alive at a known address, holds things in memory, and has its own private database attached.

You address one by name. Name it after the show — gig:perry:2026-09-14 — and Cloudflare guarantees that exactly one of those exists in the world, in one place, and every phone at that gig talks to that same one. Two people voting at the same instant are talking to the same little computer, so there is nothing to reconcile afterwards.

Every gig is a different object. A different program, on a different machine, with a different database. That is the isolation Chris is asking about, and it comes free with the model rather than being bolted on.

Hibernation is the part that makes it nearly free

The obvious worry with a program that stays alive is that you pay for it staying alive. Cloudflare's answer is the WebSocket Hibernation API, and it is the single most important fact on this page.

When nothing has happened for a short while, Cloudflare evicts the object from memory — but the phones stay connected. Their connections are held by Cloudflare's network, not by your program. The keep-alive pings that stop a connection dropping are answered by Cloudflare itself and do not wake anything.

Then somebody votes, the object is rebuilt in milliseconds, does its work, broadcasts, and goes back to sleep. In Cloudflare's own words: "Billable Duration charges do not accrue during hibernation."

The catch, stated plainly. Waking up is a fresh start — anything the program was holding in memory is gone and its constructor runs again. Anything that must survive has to be written down, either into the object's own database or attached to each connection (a per-connection attachment, capped at 16,384 bytes). This is not difficult, but it is the kind of thing that works perfectly in testing and then loses a board at a real gig if it is got wrong. Assume every message may arrive at a program that has just woken up with no memory.

Why "messages out are free" is the whole story

MySet is broadcast-shaped: one board, watched by everybody. Every time the board changes, that change has to reach every phone in the room.

A hosted realtime service prices exactly that — per message delivered. So a room twice the size costs twice as much, forever. Cloudflare prices the room and gives delivery away. For a product shaped like MySet the two are three orders of magnitude apart, and it is not because one company is better than the other. It is the shape of the product meeting the shape of the price list.

The one that is not on any limits page

A Durable Object lives in exactly one data centre — the one nearest whoever connected first — and Cloudflare's documentation does not promise automatic failover if that data centre goes away. Relocating a live object is described as planned, not shipped.

A Durable Object is a single point of failure by design. That is the price of "exactly one of these exists in the world".

This matters more than the cost table, and it is the honest answer to the redundancy question below: you do not get resilience from the open line. You get it from what the open line falls back to.

The work

What changes, and what does not

Voting barely moves

A vote still goes to Netlify. It needs the storage, the credit ledger, Stripe, the invariants — none of that should move, and moving it would be a rewrite rather than a feature. One line gets added at the end: after the write lands, tell the room the board changed.

Watching changes completely

Today every phone asks "what is the board?" every few seconds, and the server works out the answer once per phone, per ask. That is the whole scaling problem — it is why ten thousand phones is thirteen million reads a night. With an open line the board is worked out once, when something changes, and handed to everyone.

Three rules that are not optional

  1. The line is a hint; the API is the truth. Every message carries a version number, and a phone that spots a gap re-fetches once through the ordinary endpoint. Without this, one dropped message means a phone quietly showing a wrong board all night — worse than polling, not better.
  2. Polling stays. Café wifi, captive portals, corporate networks, old browsers, backgrounded tabs. The open line is an addition, and the fallback has to be tested as carefully as the main path because it is the one that runs when things are already going wrong.
  3. Reconnection storms. Ten thousand phones coming back after a wifi blip all reconnect at the same instant — straight into the 1,000-a-second ceiling. The same jitter and backoff the polling ladder already learned, applied to reconnects.

What it would not fix

Every vote still does its reads and writes on the way in. The open line removes the watching cost, which is the one that grows badly. It does not make a vote cheaper.

Chris's questions

The scaling trailheads, answered one at a time

These came from a working engineer and they are the right questions. Several of them have better answers than expected, and one has a worse one.

Question 01

Fallback servers — how do we get redundancy?

The instinct is a second copy of the same thing, ready to take over. For MySet that is the wrong shape, and the right shape already exists.

The fallback is not a mirror. It is a slower, dumber path that always works. If a room's Durable Object is unreachable — its data centre is down, the connection will not open, Cloudflare is having a bad day — the phone falls back to polling Netlify, exactly as it does today. The board updates every few seconds instead of instantly. The gig continues.

This costs nothing extra to build, because it is the system that runs now. It only costs something to keep: the polling path must stay maintained and tested forever, even once almost nobody uses it.

Recommendation: treat the polling API as the permanent floor, not as legacy. Write it into the invariants: the open line may never be the only way to see the board. A second Durable Object mirroring the first would cost more and protect less, because both would fail on the same Cloudflare outage.
Question 02

Concurrent usage — what actually happens at scale?

Two ceilings, in the order they arrive:

  • 1,000 requests a second, per object. Broadcasting is free and unlimited, so the pressure is entirely on arrivals — people opening the page. Ten thousand people arriving over ten seconds sits exactly on the line. Over ten minutes it is nothing.
  • 32,768 connections held, per object. A hard ceiling, and far above anything MySet will meet before the first one bites.

The fix for both is sharding the room: instead of one object per gig, one coordinator holding the board plus N fan-out objects, each holding a slice of the audience. The coordinator tells the fan-outs; the fan-outs tell the phones. A known pattern, and real work — call it a week on its own.

Recommendation: build the single-object version first and shard only when a booked show requires it. Sharding multiplies the duration bill by the number of objects, so it is not free — and a room under a few thousand does not need it.
Question 03

Should every feature get its own server — microservices?

The goal Chris names is exactly right: one part failing should not take the rest down. The surprise is that MySet already has this, and got it for free.

Every endpoint is its own isolated function. vote and show and community do not share a process, a machine or a memory space. If the community page throws on every request, voting is untouched. That is the isolation microservices exist to provide, without a service mesh, without network calls between services, without distributed tracing, and without twenty-five things to deploy.

What is genuinely shared is the datastore. Every function reads the same Netlify Blobs. If Blobs is down, everything is down. Splitting into microservices would not fix that — it would require a separate datastore per feature, and a vote needs the show record and the fan record in one consistent breath. Splitting them would trade an outage risk for a correctness risk, which is a bad trade in a product that takes money.

Recommendation: do not build microservices. Do isolate the one component whose failure mode is genuinely different: clips. Video is the only thing in MySet that can run away with the bill on its own, and bandwidth trouble there currently competes with the same account balance that keeps the gigs running. Moving clip bytes to Cloudflare R2 is the microservice split worth doing, and it was already on the list for cost reasons.
Question 04

Can fallback capacity switch itself on at a certain number of users?

MySet already does the safe half of this. pollFloorFor(heads) reads the head count and changes the room's behaviour automatically — slower polling, a shorter board — with no human involved and nobody refused entry.

The other half is different in kind. Automatically adding capacity means automatically spending money, and the one line item that can run away in this product is exactly the kind a threshold would trigger.

Auto-degrade, never auto-spend.

Degrading is reversible, bounded and invisible to the artist. Spending is none of those. The failure mode of an automatic capacity rule is a bill nobody chose, arriving after the night it was incurred — and on this account, running out of credit pauses every site, not just MySet.

Recommendation: keep automatic behaviour on the degradation side. For anything that costs money, put a hard ceiling in code and alert rather than scale. Auto-sharding a room is the one exception worth considering later, and even then it should have a maximum shard count that a human raises.
Question 05

Should the database have one table per show?

Yes — and MySet already does it, which is worth knowing before changing anything.

There is no shared table of votes. Each show is its own document (show_<artist>) with its own audience spread across twelve shards. One artist's gig cannot slow another's, because they do not touch the same keys.

Durable Objects make this more true rather than less. One object per gig means one program, one machine and one private SQLite database per show. A 10,000-person night and a 20-person night are not neighbours in any sense.

Recommendation: keep the per-show boundary as the fundamental unit, and name objects after the show rather than the artist — gig:<artist>:<date>. Naming them after the artist would put every night that artist ever plays through one object, which quietly re-creates the shared-table problem the current design already avoids.
Question 06 · stress test

If one gig is massive, what happens to every other gig?

On the compute side: almost nothing, and that is worth stating plainly. Functions scale per request and blob storage is per key, so a huge gig produces many independent invocations that do not queue behind anybody else's.

Three things are genuinely shared, and only one of them is dangerous:

  • The artist registry — one global document. This is why keeping it off the audience poll has had to be enforced three separate times. It stays off.
  • Platform rate limits — an account-wide concern, not currently near any edge.
  • The credit balance — and this is the real one. A runaway night burns credits from the same pot as every other site on the account. At zero credits Netlify pauses every site, so in the worst case a huge MySet gig could take iohm.io down with it.
This is the most under-appreciated risk in the whole system, and it is not a MySet risk — it is a portfolio risk. The mitigation is not architectural: keep a credit buffer, watch the balance, and know that a booked show over a few thousand people should be preceded by topping it up. Worth an alert long before it is worth an architecture.
Question 07 · stress test

What if one person starts spamming votes?

The strongest defence is already there and it is not technical: they cannot spend what they do not have. The server refuses a cast beyond the credit balance, and votes cost either the free allowance or real money. Spamming either gets refused or gets paid for.

Alongside that: each press of Confirm carries an id, so retries cannot double-charge; a single cast is capped at 50 votes; and a fan id that rotates to dodge limits is visible through the network fingerprint the room already records.

What is missing is a rate limit on the requests themselves. A script can hammer the vote endpoint and be refused ten thousand times, and each refusal still costs reads. That is not a denial of service — the gig keeps working — but it is a denial of wallet, and there is nothing in the way of it today.

Recommendation: add a small token bucket to the fan record — something like thirty casts a minute — checked inside the write that already happens, so it costs nothing extra. On Durable Objects this becomes almost free, because the object holds per-room state in memory and can simply drop an abusive connection. Worth doing before the open line, not after.
Question 08

Where are the plans, the statuses and the vision written down?

As of today, in the repository rather than in anybody's head:

  • VISION.md — what MySet is for, what it will never be, and what would make it worth stopping.
  • IMPLEMENTATION_PLAN.md — the phased roadmap, with exit criteria per item.
  • IMPLEMENTATION_STATUS.md — the living ledger: current focus, next work item, evidence, blockers, risks.
  • docs/decisions/ — one record per decision, with every option that was on the table, what it costs, what it makes harder and what would reverse it.
  • AGENTS.md — how to work in the repo, read automatically by every agent that is not Claude.
  • INVARIANTS.md — the properties that must survive every change, most discovered by being broken.
Scaffolded from Chris's own project-management skills, so the shape is one he already knows. MySet scored 64/100 — Partial against his rubric before this work; the two gaps it named were AGENTS.md and a status ledger, and both now exist.
The gap nobody had noticed

If a fan reports a bug, there is nothing to look at

This was the last question on Chris's list and it turned out to be the most urgent thing on the page.

Netlify keeps function logs for 24 hours — seven days on higher plans. Log Drains, which forward them somewhere permanent, are an Enterprise feature. So the situation today is: a fan messages Perry the morning after a gig saying something did not work, and the evidence is already gone or about to be. There is no error history, no way to see how often something happened, and no alert when something starts failing.

A bug you cannot reproduce and cannot look up is a bug you cannot fix.

How to add it without breaking the two-dependency rule

MySet has exactly two dependencies and that is deliberate. The usual way to add Sentry is its SDK, which would make it three — in the path that handles money and sign-ins.

It does not need the SDK. Reporting an error is one HTTPS POST of a small JSON envelope to an address Sentry gives you. That is perhaps forty lines of plain code with no new package — the same choice already made twice in this codebase, for the sign-in security keys and for the QR encoder, and for the same reason: a dependency in a critical path is a dependency that can be taken over.

Three rules for it, all of which follow from the existing invariants:

  1. It may never break a gig. The report is fire-and-forget; a failure to report is swallowed. Error tracking that can throw is worse than none.
  2. No secrets, no fan device ids, no personal data in the envelope. The message and the stack, not the payload.
  3. Off without its key, and off is a clean no-op — the same shape as Stripe and the Google Sheet.
This is the cheapest item on the page and it closes a gate nothing else closes. It is worth doing before the shared-board split, because the split is the first change big enough that you would want to know if it quietly broke something at a real gig.
The order

What to build first

Ranked by what each one buys divided by what it costs to own afterwards.

1

Error tracking

Forty lines, no new dependency, free tier. Turns "a fan said something broke" from an unanswerable message into a stack trace with a count next to it.

2

A rate limit on casting

A token bucket on the fan record that is already being written. Closes the denial-of-wallet hole before there is more surface to defend.

3

The shared-board split

One cacheable board with no fan id in the address, plus a tiny per-fan call. Removes the same quadratic the open line removes, on the platform that already runs everything.

~5 days · no new vendor · gates the plan room sizes

4

Clips onto Cloudflare R2

Opens the Cloudflare account, and isolates the one component that can run away with the bill. Storage costs pennies and serving is free.

~2 days · needs Perry's own Cloudflare account · trigger: ~100GB of clip traffic a month

5

The open line

Durable Objects, one per gig, hibernating between votes, with polling kept as the permanent floor beneath it.

1.5–2 weeks on top of the split · trigger: a booked show over 2,000 people, with a date and a deposit

Why the open line is fifth and not first. It is the best end state and nothing above contradicts it — items 3 and 4 are both steps toward it. But it adds a platform, and a platform is not a one-off cost. It is a second thing to deploy, a second thing to watch, a second bill, a second outage page to read at a gig, and a fallback that has to be kept alive forever. The four items above buy most of the same headroom without any of that, and item 4 opens the Cloudflare account anyway — so by the time the open line is worth building, the account, the credentials and the habit already exist.
Still open

What this page does not know

Unmeasured

The shared-board estimate is arithmetic, not a benchmark

~$0.55 for a 10,000-person gig assumes the board becomes a single cached read. It has not been built or measured, and caching on Netlify has already surprised this project once.

Unmeasured

The write wall is derived from a read

The ~11,000-voter write ceiling comes from a measured 40ms read, never from a measured write. If a write is four times slower, the wall arrives at 4,000 people. Hammer one shard before selling a room over 2,000.

Untested

Nothing here has been run

Every Cloudflare figure is list price applied to MySet's own measured traffic. No object has been created, no connection opened, no message sent. The first real number should come from a throwaway test, not from a gig.

Unknown

What a real reconnection storm does

Ten thousand phones reconnecting after a wifi blip is the scenario most likely to hit the 1,000-a-second ceiling, and it is the one that cannot be reasoned about — it has to be simulated.

Unknown

Failover behaviour in practice

Cloudflare documents no automatic relocation for a live object. What actually happens to a room when its data centre has a bad day is not written down anywhere public.

Decision

Whether a room over 2,000 is ever sold

Everything above item 3 is optional until a real booking exists. The trigger has been the same since September 5th: a date and a deposit.
