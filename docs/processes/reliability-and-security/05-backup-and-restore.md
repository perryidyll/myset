# Backup and restore

**Who:** the founder, with an agent. **Trigger:** today, then on a rhythm; and the day something is gone. **Outcome:** a copy of the one datastore that exists somewhere Netlify is not, and a restore that has been **rehearsed** — because *an untested backup is a rumour*. **Status (2026-10-02): two copies, both read back.** The laptop copy (`tools/backup.py`, weekly, dated) and the nightly copy on R2 (`mirrorcron`, decision 0069). A restore has been rehearsed from each into a separate store: from a laptop copy on 2026-09-14, and from the R2 copy on 2026-10-02 (258 of 258 keys, read back equal). Since decision 0146 every kind of document is either copied or named with a reason, and the suite fails on a kind nobody classified. Never done, by design: a restore into the production store.

| b04 | Restore into a separate store | task | AI Agent | Coding agent R · Founder A | Netlify | `python3 tools/backup.py --restore DIR --store rehearsal-YYYYMMDD` writes every key in a copy's manifest into a separate store on the same site (the functions only ever open `myset`), reads each back and compares its checksum; `--wipe` clears it afterwards. DIR is a laptop copy (b03) or an R2 pull (b10) — the same folder shape. It **refuses the production store by name**: a restore into `myset` bypasses every etag and every invariant the functions enforce (§5.2 rule 4), and is done by a person, on the day the data is gone. **Rehearsed twice:** 2026-09-14 from a laptop copy (209 keys, 580 s) and 2026-10-02 from the R2 copy (258 keys, 687 s) — about 2.7 s a key, so the time grows with the store.
