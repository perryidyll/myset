# Watching production

**Who:** the founder, or an agent on the founder's machine. **Trigger:** a session starts; a gig just happened; the Netlify bill arrives; a fan said something. **Outcome:** the live site's state read without anyone's password, the cost of a night known before it is sold, and the ledger's open-risk table kept honest. **Until decision 0157 everything here was pulled by a person and nothing pushed.** u09–u11 are the part that asks by itself: a watch inside MySet every ten minutes, a health address, and a check from outside that opens an alert when the site stops answering.

| u09 | Ask the three questions | conditional | Automation | Scheduled jobs R · Founder I | Netlify | **Built, not live** (decision 0157, pull request #213). `watchcron` runs every ten minutes and does only what `_watch.mjs` does. Three questions with yes-or-no answers, read fresh each time: **bell** — did `autocron` ring in the last `BELL_STALE_MS` (ten minutes, from `gigsched.lastRunAt`)? Shows start and end from it. **owed** — is any payment in `payowed` still undelivered after `OWED_STALE_MS` (fifteen minutes; decision 0138, → *The gig → Shows that start and end themselves* s13)? **errors** — did the last hour log `ERRS_PER_HOUR` (25) or more server errors (→ *When something breaks* i02)? A store that does not answer is itself an answer (**store**). every answer inside its limit → nothing is said; an answer changed → *When something breaks on the night* i09. Logged, never thrown. **What it cannot see is itself**: if Netlify stops running scheduled functions, or the site is down, this is down too — that is u11's job. `src: _watch.mjs look, watch; watchcron.mjs; decision 0157; test/watch.mjs` |
| u10 | Answer the health address | conditional | Automation | MySet server R | Netlify | **Built, not live** (decision 0157, pull request #213). `GET /api/health` — for a machine that is not MySet to ask. Never cached, a handful of small reads, **ages and counts only**: `bellAgeSec`, `owed`, `owedOldestSec`, `errorsLastHour`, `watchAgeSec` and the limits — no names, no amounts, nothing a stranger learns anything from. **200** with `ok: true` when every answer is inside its limit; **503** otherwise, with `why` (`bell`, `owed`, `errors`, `store`, `watch`), and 503 "busy" when the store does not answer at all. `watchAgeSec` is how long since the inside watch (u09) last ran; past thirty minutes it is a `why` of its own, which is how an outside check sees a stopped schedule. It is also the address a monitoring service would point at, if one is set up later. `src: health.mjs; _watch.mjs look; decision 0157; test/watch.mjs` |
| u11 | Check from outside | conditional | Automation | Scheduled jobs R · Founder I | GitHub | **Built, not live** (decision 0157, pull request #213 — a scheduled workflow only runs from `main`). `.github/workflows/watch.yml`: every five minutes GitHub's machines read `/api/health` (u10) and the front page — by content, not by status (u02). Three tries, forty seconds apart, before anything is called down. It speaks only when the answer changes: **down** → it opens one issue, *"MySet is not answering"*, labelled `uptime` and assigned to the repository's owner, which GitHub sends to their email and phone; **up again** → it closes that issue with the time; while the issue is open it says nothing more. If the repository has a secret named `NTFY_TOPIC`, both messages also go to ntfy.sh as a phone push. GitHub starts scheduled workflows late when it is busy — five to thirty minutes — so this is **a backstop, not a stopwatch**. The repository is public, so an outage leaves a public issue; it carries the health address's counts and nothing else. A monitoring service would be the faster outside check and would replace this workflow, not the health address or the inside watch. **Not checked:** the workflow on GitHub's schedule; how late GitHub actually starts it. `src: .github/workflows/watch.yml; decision 0157` |
