# Shows that start and end themselves

**Who:** the scheduled function (role *Scheduled jobs*). **Trigger:** `autocron.mjs` rings every two minutes (`schedule: '*/2 * * * *'`). **Outcome:** a calendar gig's show is live at its start time even if the artist forgot, and ended a grace period after its scheduled end even if they walked off stage without tapping — and an idle show is ended so nothing runs all night. Neither path ever touches the audience poll. Since decision 0140 the bell does what a room is waiting on first and its housekeeping on a clock; since decision 0138 it also retries a fan's payment that a webhook could not deliver.

The founder's rule (2026-09-04): a gig on the calendar starts its show at the gig's start time if the artist hasn't already, and ends it three hours after the gig's scheduled end if the artist hasn't already. Decision 0021.

| s01 | Ring | signal | Automation | Scheduled jobs R | Netlify | Every two minutes. A show can therefore start up to two minutes late — inside what the room notices. Same discipline as the sheet cron: the scheduler's `next_run` marker is logged, never enforced; errors are **logged, never thrown** (a thrown scheduled function is retried). **The order is the point** (decision 0140, INVARIANT 0ho): what a room is waiting on goes first — shows starting and ending (s04–s09), idle shows (s10), payments still owed (s13), the first-night letter — and the housekeeping (s11, s12) gets only the time that is left. Nothing new is begun after `RING_BUDGET_MS` (seven seconds: Netlify's documents give a scheduled function thirty, and the one kill this repo has measured came at about twelve, decision 0069). Each step is caught on its own, so one failing is logged and the rest still run. The warm pings (decision 0049) are started alongside the ring and awaited at the end; they used to be awaited first, for up to eight seconds, before a single show was looked at. `src: autocron.mjs header, RING_BUDGET_MS, ring(); decision 0140` |
| s02 | Take the lock | conditional | Automation | Scheduled jobs R | Netlify | Skip if the last run was seconds ago; *"another run is in progress"* / *"lost the lock"* → return 200 `busy`. Two rings cannot act at once. `src: autocron.mjs 37–52` |
| s03 | Read the one index | database | Automation | Scheduled jobs R | Netlify | `gigsched` — one global document rewritten by every calendar write (the `cityindex` pattern, INVARIANT 0i). A tick reads **one** document to learn who has a gig due; it never `list()`s (INVARIANT 1) and never walks every artist's calendar (9d13). A quiet ring costs one read. Since decision 0140 the document also carries the bell's own marks: on an entry, `skip` (a start that was refused, s06) and `on` (a night already under way, s05); on the document, `sweepAfter` and `idleAfter` (where the last ring's two sweeps stopped), `live[aid]` (each live show's last known sign of life, s10) and `healCursor` (s11). Any code that rewrites an entry for the same night must keep the marks or drop them on purpose: `reindexSched` keeps `skip` and drops `on`; the daily pass keeps both. `src: _auto.mjs; overview §5.7; decision 0140` |
| s04 | Is a gig due to start? | conditional | Automation | Scheduled jobs R | Netlify | Now is inside the occurrence window, the start was not refused (`skip`), and the night is not already under way (`on`) — or the gig is past its end plus the grace period (s07). Venue-owned events (`v_…`) are never shows. **Bounded, and bounded no longer means never** (decision 0140): at most 40 entries a ring, `SWEEP_POOL` (five) artists worked at once, none begun after the ring's deadline — and what is due is walked in id order starting after the last artist the previous ring reached (`sweepAfter`), so a ring that runs out of room or time leaves the rest first in line. Until then the sweep took the first 40 due entries every ring and a gig under way stayed due for its whole length, so the forty-first gig in progress was never looked at: it did not start itself and it did not end itself. `src: _auto.mjs sweep; decision 0140; INVARIANT 0bw` |
| s05 | Start the show | task | Automation | Scheduled jobs R · MySet server R · Artist I | Netlify | `startShow(aid, {by:'schedule', occKey, eventId})` — the **same** function the Studio button calls, so the gig cap, the archive, tonight's setlist, the venue name and the paid-vote carry happen identically (9d9, 17c, 13b). The occurrence key is stamped on the show so the same gig is **never started twice**, and a night the artist ended early **stays ended**. Won't start with no songs switched on. **Never for an account on its way out** (0dh, decision 0098): `deletionOf` is asked right before the start — the check a tap on Start meets — and the account's entry is taken out (`drop`), not re-pointed at its next gig. The Live tab says *started by itself*. **A settled night is marked `on`** (decision 0140): `autoTick` returns `settled` when tonight's start is decided for good — started now, already live, already started once, or ended by the artist — and the sweep marks the entry `on` for that night, so the next ring reads only the index and the entry is due again only when its end is. Not settled, on purpose: *no songs switched on* and *auto-start is off* — either can change mid-gig and the next ring should act on it. The mark is dropped by any calendar write. `src: _lifecycle.mjs; _auto.mjs autoTick, sweep; decision 0140` |
| s06 | Cap refused? | conditional | Automation | Scheduled jobs R · Artist I | Netlify | A free-plan cap refusal is remembered on the index entry so it is **not retried every two minutes** for the rest of the night. `src: _auto.mjs header` |
| s07 | Is a gig past its grace period? | conditional | Automation | Scheduled jobs R | Netlify | `now ≥ endsAt + END_GRACE_MS` and the show is live. If the show started **after** that moment it is *a later show* and left alone. `src: _auto.mjs 151–153` |
| s08 | Is a song still recent? | conditional | Automation | Scheduled jobs R | Netlify | A song started within `IDLE_MS` means the set is still on → **defer to the next tick** (never end mid-song, INVARIANT 16) — unless the show is *stale* (six hours past the grace period), in which case it ends anyway. `src: _auto.mjs 161–162` |
| s09 | End the show | task | Automation | Scheduled jobs R · MySet server R · Artist I · Fan I | Netlify | `endShow(aid, {by:'schedule'})` — archive first, always. The Live tab says *ended by itself*. **A night where nothing happened — no song, no vote, no phone — is not archived**, so an empty scheduled start never becomes "Shows: 1". `src: _lifecycle.mjs endShow; overview §5.7` |
| s10 | End idle shows | task | Automation | Scheduled jobs R · Artist I | Netlify | Any live show with nothing happening for `SHOW_IDLE_MS` is ended (*"ended after three idle hours"*) — the guard against a show left running all night burning polls. Decision 0021. The list it reads (`live`) is filled by the live walk in the register's bell, not by the start: a show started by hand reaches it within one lap, stamped with its own last write (decision 0154). Since decision 0140 `live[aid]` is the show's **last known sign of life**: a show active less than three hours ago by that mark cannot be idle and costs no reads; one that is looked at (the show and its twelve fan files) and found busy has its mark moved up, so it is read again in three hours, not in two minutes. What is left is walked like s04 — in id order from where the last ring stopped (`idleAfter`), at most 40, none begun after the deadline. Until then it was the first forty live shows, every ring, so the forty-first could never be ended for inactivity. `src: _auto.mjs sweepIdle; decisions 0021, 0140` |
| s11 | Heal the index | task | Automation | Scheduled jobs R | Netlify | Once a day: walk the artist registry (one global read) and re-point every artist from their own calendar (one read each), in batches with a cursor — catches gigs saved before the index existed and any entry a lost write dropped. **After the sweeps, on the ring's clock, a chunk at a time** (decision 0140): `HEAL_CHUNK` (ten) calendars are read together and land in **one** write that also moves the cursor, and the deadline is checked between chunks — a ring that runs out of time has saved everything it did, the next ring carries on, and the day is stamped healed only when a full pass completes. A chunk never puts back an entry somebody changed while its calendars were being read, and the same night keeps its `skip` and `on` marks. Until then the pass ran **first**, one read and one write per artist in series, with no clock and the cursor saved only at the end — so past a hundred artists or so the platform would have killed the ring before it reached a single show, and every ring after it the same way. Not checked: a real ring on production with many artists (the registry held six on the day of the audit). A row **marked for deletion is skipped**: it came off the index on day one and stays off for the thirty days; Undo re-indexes it (0dh, decision 0098). `src: _auto.mjs "THE HEAL", HEAL_CHUNK; autocron.mjs; decisions 0098, 0140; test/autoshow.mjs` |
| s12 | Sweep the leftovers | task | Automation | Scheduled jobs R | Netlify | Purge expired rows; drop unposted clips left in `vidqueue`. Each in its own try/catch, logged — and, since decision 0140, each begun only while the ring still has time left. `src: autocron.mjs; decision 0140` |
| s13 | Retry owed payments | payment | Automation | Scheduled jobs R · MySet server R · Fan I | Stripe | **Live** as `0387145` (decision 0138, PR #205). After the two show sweeps and before the housekeeping, `redeliverOwed` reads the one global document `payowed` (→ *Money → Stripe events arriving* w12) — one small read a ring, and nothing more when nothing is owed. For each row, least recently tried first, at most ten a ring and none begun after the ring's deadline: read the session back from Stripe (in the connected account's scope) and, if Stripe says it is paid, `redeemSession` — the same grant the webhook, the return page and the artist's sweep use (→ *Buying votes and tipping* b10, b11). Delivered, or already delivered by Stripe's own redelivery or the buyer's return trip → the row is cleared. Failed again → the try is counted and it waits for the next ring. A row older than three days is dropped without asking Stripe; the Money tab still shows that payment as not delivered and the artist's sweep still recovers it. Never throws. A payment still owed after fifteen minutes is one of the three things the watch tells the founder about (→ *Reliability & security → Watching production* u09). `src: autocron.mjs; _pay.mjs redeliverOwed; decision 0138; INVARIANTS 0hm, 5c, 7b; test/delivery.mjs` |

## Nine ways a night could vanish (closed 2026-09-05)

Worth keeping on the canvas as notes on s05/s09, because they are the shape of the bugs this section exists to prevent: a Stripe hiccup that threw past the archive into an empty catch; an index row built from the wrong snapshot; two writes ending in `.catch(() => {})`; a `status === 'pre'` guard that made every later archive return null for ever; an index cap of 100 that stranded row 101 invisibly; and a browser cache never invalidated, so ending a show made the night *look* lost. The **heal** behind *Look for missing shows* rebuilds an artist's index from every id it can name. `src: overview §5.7`
