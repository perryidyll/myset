## What shipped (in the worktree)

- `netlify/functions/_r2.mjs` — **new.** AWS Signature Version 4 in `node:crypto`:
  `sigv4()` (canonical request, string to sign, signature), `presign()` (query-string
  auth), and `r2Put` / `r2Head` / `r2Get` / `r2Delete` / `r2PresignGet` against
  `https://<account>.r2.cloudflarestorage.com/<bucket>/<key>`, region `auto`. Every
  call has a timeout (PUT 8s, GET 20s, HEAD 4s, DELETE 6s). `r2Enabled()` is true only
  with all four variables set. PUTs carry the SHA-256 of the body so a mangled transfer
  is refused by the bucket. `LINK_SECS = 4h`, `CACHE_SECS = 1h`; links are signed from
  the top of the hour so the edge and the browser see one URL per clip per hour.
- `netlify/functions/_video.mjs` — `putClip` sends to R2 and falls back to Blobs;
  `getClip` reads R2 first (`r2:false` to skip it); new `hasClip` (one HEAD, for the
  existence check in `addPost`), `clipUrl` (presigned link or null), `dropClipKeys`
  (the R2 half of an account's key list), `vidKey` (the one spelling of the key, now
  used by the two delete lists too); `dropClip` deletes from both stores and returns
  false if R2 refused — in which case the clip is re-noted on the pending list and the
  sweep retries it. `sweepQueue` keeps an owner on the ring while their pending list is
  non-empty (it used to drop them after one visit). Every R2 failure is logged through
  `logErr` (0fb), at most once a minute per instance per kind, and never carries a key
  or a link.
- `netlify/functions/vid.mjs` — a clip on R2 is a **302** to the signed link, cached an
  hour (`public, max-age=3600`, `durable`, never `immutable`). A clip in Blobs is served
  as before, year-long immutable, with the Range handling untouched.
- `netlify/functions/_community.mjs` — `addPost` asks `hasClip` instead of pulling 75MB
  through the function to answer yes.
- `netlify/functions/_account.mjs`, `_venueaccount.mjs` — `deleteArtist` and
  `deleteVenue` call `dropClipKeys(keys)` after the Blobs walk.
- `test/r2-fake.mjs` — **new.** An in-memory bucket behind `globalThis.fetch` for the R2
  host only. It **re-derives every signature from what was actually sent** (headers and
  query styles), checks the presigned link's expiry against an injectable clock, checks
  the PUT body hash, answers Range with a 206, and can be told to answer 503, to throw,
  or to be reset. Same idea as `test/stripe-fake.mjs`.
- `test/clips.mjs` — 77 new assertions (163 total; the first 86 unchanged and green with
  R2 off). See decision `0033` § "How it was verified" for the list.
- `tools/overview.mjs` — §2.1 gains "A clip link on R2 lives / its redirect is cached",
  read from `_r2.mjs`.
- INVARIANT **0fd**; decision **0033**; this file; the ledger (P3-003 done).

**Untouched, on purpose:** `MAX_VIDEO_BYTES` (75MB, 0ev), `public/mp4trim.js` (0ew),

## How fans fetch clips — the decision

`myset.vip`'s nameservers are NS1 (`dns1-4.p04.nsone.net`), i.e. **Netlify DNS**, with
Porkbun as registrar. A Cloudflare custom domain on the bucket needs the zone on
Cloudflare, so it is not available without moving a live site's DNS. `r2.dev` is
rate-limited and not for production. So: **`/api/vid` answers a 302 to a presigned GET**
on the bucket's own S3 endpoint, bucket public access stays **off**. The page's `<video>`
tags carry no `crossorigin` attribute, so the cross-origin redirect needs no CORS on the
bucket. Decision `0033` has the option table.

## Migration note — clips that already exist

Nothing is copied in bulk. `list()` is banned (INVARIANT 1), and a copy that half-fails
is worse than none. Every clip uploaded before this change is in Blobs under
`vid_<owner>_<clip>` and **keeps serving from Blobs**: `/api/vid` asks R2 (one HEAD,
404), then Blobs, and the year-long immutable cache on those responses is unchanged.
Netlify egress continues to be billed for THOSE clips only. They leave the way they
always did — when the post is hidden or deleted, when the account goes, or when the
artist re-uploads.

If it ever matters (the 2026-09-06 trigger was ~100GB/month of clip traffic; how many
clips exist today was not counted — it would take a walk of every owner's posts), the
path is a one-off tool that walks
`posts_<owner>` for every owner in the artist and venue registries (computable keys, no
`list()`), reads each `vid_` key from Blobs, `r2Put`s it under the same key, verifies
with `r2Head`, and only then deletes from Blobs. It has not been written because there
is nothing yet worth the risk of running it against production.

## The order to deploy in, and what to look at after

1. Merge `claude/r2-clips` onto `main` when the user says so — after the split has
   landed, or before it; the two do not overlap in code. Run `sh test/run.sh` first.
2. `git push` is the deploy. **No `netlify deploy`** (9d3).
3. Afterwards, from outside: upload a clip on a community page, then
   `curl -sI 'https://myset.vip/api/vid?a=<owner>&c=<clip>'` should be a **302** with a
   `location:` on `r2.cloudflarestorage.com` and `cache-control: public, max-age=3600`.
   Then play it on a real iPhone. If it does not play, the phone is not carrying its
   Range through the redirect and the fallback is a custom domain (needs the DNS move)
   or proxying (which gives the saving back).
4. A wrong key shows up as `r2.put 403` rows in the error log (bug reports read them,
   `admin` action `bugList`), and the clip still lands in Blobs — nobody in the room
   sees it.
5. **Do not remove the four variables once a clip is on R2.** Every clip there becomes
   a 404 and every later delete skips it. Rotate a key by replacing it.

## What was verified, and what was not

- `node tools/overview.mjs --tests` in the worktree: exit 0, **2,004 assertions, 0
  failing**, stamped into the overview.
- `test/clips.mjs` alone: 163/163, including the AWS vectors and the fake's own
  signature refusal of a wrong secret.
- An independent fresh-context review of the diff ran the suite itself (same numbers,
  before the last ten assertions were added) and captured the raw TLS bytes undici
  sends for PUT/HEAD/DELETE, re-deriving SigV4 with its own code: all three matched.
  Its findings and what was done about each are in decision `0033`.
- Signer checked by running it against Amazon's published example before any test was
  written: header signature `f0e8bdb8…`, canonical hash `7344ae5b…`, presigned
  signature `aeeed9bb…` — all three matched.
- A measurement trap caught and fixed: the delete tests first passed while the fake was
  throwing on a bodied 204 (deleted before the throw). Fixed; an assertion now demands no
  `r2.delete` error row.
- **Not verified:** any request against the real bucket (keys live in Netlify only, by
  design); playback on a real phone through the 302; the function's wall-clock for a
  75MB PUT to Cloudflare from Netlify's region. Netlify's documented default budget for
  a synchronous function is 10s and the `end` step has already read every piece back
  before the PUT starts. The PUT gives up at 8s and falls back to Blobs — but a 75MB
  Blobs write after an 8s stall may not fit either, in which case the upload fails
  with the existing "try again" and the room is unaffected. **The first real 75MB
  upload after deploy is the measurement.** If it fails, the fix is to lower the PUT
  timeout or to move the R2 PUT into the piece-by-piece path (S3 multipart) — a
  larger change, not started.
